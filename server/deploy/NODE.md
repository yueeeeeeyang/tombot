# 节点离线镜像安装

将对应架构的节点程序包和电脑镜像包解压到同一个新建的受保护目录（例如 `/root/tombot/`）。核对受信渠道提供的归档摘要后，在该目录执行以下命令。

```sh
sha256sum -c PROGRAM-SHA256SUMS
sha256sum -c SHA256SUMS
sudo ./tomnode install
```

粘贴管理平台“电脑节点 → 生成接入凭据”中新生成的接入码，再确认服务端可访问的节点地址。默认无需准备 `node-install.json`，无需填写服务地址、证书指纹、镜像摘要或软件包版本。

程序包提供五个可执行文件，镜像包提供 Debian、Chrome 和桌面工具。安装器校验本地镜像后自动导入 Docker。**Docker 与宿主依赖仍从官方软件源安装，需要联网**。节点还需访问服务端。镜像不依赖远程仓库，不在离线导入失败时回退到联网拉取。

支持 Debian/Ubuntu 与 RHEL/Rocky/AlmaLinux/CentOS Stream/Fedora 家族，不按系统版本号或工具补丁版本设置白名单。需要 systemd、cgroup v2，以及支持 Engine API 1.47 的 Docker；amd64/arm64 必须使用与宿主和离线镜像匹配的包。安装依赖当前发行版仍可用的签名软件源，不把已停止维护的软件源切换到其他发行版。文件和整个父目录链须由 root 或此次 sudo 调用者持有，不得组写、其他用户写入、含符号链接或硬链接。不要从公共 `/tmp/` 目录直接安装。

## 自动填写与可选参数

接入码封装服务端 HTTPS 来源、固定证书指纹与一次性授权。安装器先核对证书，再通过已鉴权接口取得 API 客户端证书指纹和验收资源预算，不使用首次连接返回的证书建立信任。服务端 `admin_origin` 必须是节点实际可达的 HTTPS 来源，不能配置为远程节点无法访问的本机回环地址。

节点名称默认取主机名加唯一后缀；容量按 CPU、内存、可用磁盘及独立验收预算计算，最多 7 台业务电脑。容量只是安装建议，实际就绪状态仍由服务端能力验收决定。单网卡自动选择监听地址；多网卡或 NAT 场景由安装者确认本机监听地址及服务端可达地址。默认控制端口为 9444，服务端默认 9443，同机部署也使用独立端口。节点访问地址不能与服务端来源相同；首次安装会提前检查监听端口是否可绑定。请只向 API 来源放行节点端口。

需要覆盖时才生成可选参数：

```sh
./tomnode template > node-install.json
```

初始内容为 `{}`，仅支持以下四项；不需要全部填写：

| 字段 | 用途 |
| --- | --- |
| `node_name` | 自定义唯一节点名称 |
| `computer_capacity` | 降低建议容量，不得超过资源计算结果 |
| `listen` | 本机监听的 `IP:端口`，IPv6 使用方括号；通配地址需显式指定 |
| `node_url` | 服务端可访问的节点 HTTPS 来源；NAT 或端口映射时填写实际地址 |

显式使用参数文件：

```sh
sudo ./tomnode install /绝对路径/node-install.json
```

不传路径时不会自动读取当前目录的同名文件。参数文件拒绝未知字段、重复字段、空值、尾随对象及超过 16 KiB 的内容。接入码输入不回显；Ctrl+C、终端关闭或五分钟超时会取消。不要把接入码写入 JSON、命令行、环境变量或日志。

## 运行与接入

安装命令自动创建身份和证书、保存配置和归档、安装程序及 systemd 单元、设置开机启动，并等待控制服务启动和自动接入。多个节点分别使用独立接入码，管理平台无需手动登记。

```sh
sudo systemctl status tombot-node
sudo systemctl restart tombot-node
sudo journalctl -u tombot-node -f
```

| 位置 | 内容与权限 |
| --- | --- |
| `/usr/lib/tombot/tomnode` | 节点程序，root 0755 |
| `/usr/lib/tombot/programs/` | 电脑基础代理和 Bot 的版本目录，容器只读挂载 |
| `/etc/systemd/system/tombot-node.service` | 内置服务单元，root 0644 |
| `/etc/tombot/node/` | root 0700；内含三份运行配置、证书、私钥、`enrollment.token`、`computer-image.tar` 及安装记录，均为 root 0600 |

原始授权值由程序私有保存，完整接入码不落入安装配置。离线归档保留用于本机镜像丢失后的恢复，安装及重试会校验 SHA-256，导入后还会核对固定镜像摘要、平台和电脑入口约定。需为安装包、归档副本和 Docker 镜像存储预留空间。

服务执行 `tomnode start`，按配置检查、宿主软件准备、固定镜像准备、节点恢复、自动接入顺序运行。宿主安装与镜像准备各最多一小时，服务启动上限 140 分钟，安装器最多等待 141 分钟。取消安装等待不保证已启动的 systemd 作业停止，先查看状态再用原命令重试。高级诊断见 `tomnode help` 与 `tomnode check`。

`state: control_started` 只表示控制服务已启动。浏览器、网络隔离、存储等能力验收通过后才可创建用户电脑；真实 Ubuntu 首次安装、挂载配额及 cgroup 回收需实机验收。

## 宿主机关机与电脑恢复

系统关机时，systemd 先停止 `tombot-node`，让节点在 Docker 仍可用时清理会话。受管电脑容器使用 `RestartPolicy=no`。节点启动时先回收持久化记录中的旧会话，再核对已停止电脑的容器和磁盘归属，启动原容器并检查就绪状态。恢复后继续使用原容器 ID、用户磁盘和浏览器数据，沿用旧会话的围栏记录。电脑通过就绪检查后才接受新会话，中断的消息任务需由用户重新发起。

单台电脑恢复失败时，节点按用户和容器标识记录失败，保留恢复记录并暂停该电脑的新会话。用 `sudo journalctl -b -u tombot-node --no-pager` 定位问题。解决故障后执行 `sudo systemctl restart tombot-node`，节点会重试恢复原容器。旧会话回收未确认、出网无法封闭或整体启动超过 `startup_timeout_ms` 时，节点拒绝启动。

现有节点按下节按组件升级，需修复已停止的节点时使用 `tomnode repair`。升级后运行 `sudo systemctl show tombot-node -p After`，确认输出包含 `docker.service`。在独立的 Linux 节点上重启宿主机，检查停服及恢复日志，核对容器 ID、磁盘和浏览器数据，再发送一条消息验证新会话。

回滚按下节操作，并保留电脑磁盘和节点持久状态。仍有未确认恢复的电脑时，在维护窗口停止对应原容器后再切换到旧版。重新部署新版节点后可继续恢复。

## 重试、升级与回滚

完成首次切换后，可在新建的私有目录解压程序包，执行 `sha256sum -c PROGRAM-SHA256SUMS` 和 `sudo ./tomnode upgrade`。单独更新镜像时，将镜像包解压到另一私有目录，执行 `sudo /usr/lib/tombot/tomnode upgrade --image-package /绝对路径/镜像包目录`。安装器复用节点身份、证书和用户盘。

从共享浏览器版本升级时，安装器先按 `installation.json` 核对原始 `node.json` 的摘要及节点 ID，再从运行配置和安装请求中移除退役的 `browser.limits`。浏览器的超时设置继续生效。原始文件随本次升级备份，可按下文成套回滚。遇到摘要或 ID 冲突时，先核对该节点的成套备份，手工修改配置或重算安装记录会破坏核对依据。

安装锁串行保护首次安装，配置、身份和归档在私有目录写完、刷盘后原子发布。中途失败保留已发布身份；使用同一二进制和相同选项重试，复用本地安装快照，不再询问接入码或依赖原始发布清单、镜像归档。JSON 缩进与字段顺序不影响重试。快照、凭据、归档、证书、程序或单元被修改时明确失败，不覆盖或重新生成身份。

Docker 引导清单改为版本 2，只保留超时与磁盘余量；发行版适配器提供包名、官方软件源及签名指纹。旧清单不会在启动时被静默忽略，需要修复命令显式迁移。独立发布包使用格式 2，节点安装记录保持版本 2，不涉及业务数据库迁移。

旧安装失败、需要替换程序或修正端口时，先停止节点，在新程序所在目录执行：

```sh
sudo systemctl stop tombot-node
sudo ./tomnode repair --listen 本机IP:9444 --url https://服务端可达的节点地址:9444
```

地址正确时只需 `sudo ./tomnode repair`。修复会核对原安装快照、程序、身份和镜像摘要，备份待变更文件，迁移运行配置及安装记录，然后启动节点；不要求重新输入接入码，不重新生成节点 ID、证书、私钥，不重新复制离线镜像。运行中的节点必须先排空；不会自动停止有任务的服务或覆盖手工改动的配置。修复后的普通重试仍可使用原安装命令。

修复过程中断时，使用同一新程序和同组选项再次执行。`/etc/tombot/node-repair/` 保存待完成计划及前后文件摘要；仅接受原值或计划中的新值，其他变化明确失败。完成后备份归档到日志所示的 `/etc/tombot/node-repair-<标识>/`，权限 0700，内部文件 0600。出现启动故障时保留此目录和 `/etc/tombot/node/`，不要删除身份。

回滚须先停止服务，将所选备份 `before/` 中的 `program`、`service` 分别恢复到 `/usr/lib/tombot/tomnode`（0755）、`/etc/systemd/system/tombot-node.service`（0644），将四份 JSON 恢复到 `/etc/tombot/node/`（0600），然后 `systemctl daemon-reload` 并启动；不能混用不同备份的文件。未完成的修复应先用原命令恢复完成再回滚。修复不修改业务磁盘或数据库，已安装的系统软件及镜像层不自动降级或卸载。旧程序恢复后仍会执行旧版本约束，回滚不能消除原先的宿主版本不匹配。

证书有效期一年，维护时提前安排续期。节点完整能力仍由实际挂载、配额、网络和浏览器验收决定，发行版单元测试或容器工具检查不能替代完整 systemd 主机验收。多节点接入的历史数据库迁移及回滚要求见[接入说明](../docs/node-registration.md#升级与回滚)。

完整浏览器探针需要配套电脑镜像。旧节点请按[浏览器能力验收与升级](../docs/browser-readiness.md)保留身份升级离线包。

## 管理平台远程升级

**日常操作。** 在「电脑节点 → 远程升级 → 上传新版本」选择节点程序包。桌面基础环境发生变化时才上传电脑镜像包。服务端从包内读取类型、版本和架构，流式校验包内成员和压缩分片，成功后可选择目标节点下发。节点通过已绑定的 HTTPS 服务领取任务，再核对分片和程序摘要。发布授权来自通过身份复核的管理员，SHA-256 用于检验内容完整性。上传中断时，重新选择同一文件即可续传。相同归档已登记且仍在服务端时，浏览器按摘要复用，只传版本确认请求。已有发布包可直接选择目标版本；添加其他版本时点击「上传新版本」。选择本页节点或「所有同架构节点」后下发，后者覆盖其他分页中已启用更新器的同架构节点。任一目标节点已有等待或运行中的升级任务时，整批下发返回冲突。节点约每分钟主动轮询已绑定的服务端，无需开放 SSH 或新的入站端口。默认最多三个节点同时领取新任务，长时间无回执的任务不永久占用名额。离线节点保留队列；未启用更新或架构不匹配的节点不能执行。

**首次切换。** 在维护窗口排空旧升级任务，保存数据库、用户磁盘、节点身份、安装目录及原发布包的一致备份。先升级配套的 `tomd`，再把格式 2 的程序包和带 `io.tombot.computer.external-programs=1` 的镜像包解压到节点上的同一私有目录，核对两份清单，在该目录执行一次 `sudo ./tomnode upgrade`。旧节点需要这次本地操作来启用新版更新器和容器只读挂载。本次拆包沿用归档校验表，无新增数据库迁移。

如果升级报「tomnode 与当前节点包的 SHA256SUMS 不匹配」，先看解包目录中哪份清单列出了 `tomnode`。旧版完整包把它写在 `SHA256SUMS`，拆分程序包把它写在 `PROGRAM-SHA256SUMS`。两份都列出时，说明目录混用了两代发布文件。保留原目录，另建空目录重新解压。首次切换用两个新包，已经完成切换的节点日常升级只解压程序包。若使用旧完整包，也须从该包解压配套的程序和清单。

| 变更内容 | 需上传 | 节点上的行为 |
| --- | --- | --- |
| 仅 `bot-agent` | 程序包 | 原子切换 Bot 入口，已有进程继续运行，下次启动使用新版 |
| `tomnode` 或三个电脑基础代理 | 程序包 | 取得维护权并重启节点服务。基础代理变更时，在旧会话关闭后重启原电脑容器并复验，沿用同一镜像和用户盘 |
| 系统、Chrome、桌面工具或镜像入口 | 镜像包 | 节点按摘要导入，既有电脑在原磁盘上切换到新镜像 |

节点按内容摘要存放基础代理和 Bot。旧程序目录保留用于尚未退出的进程及回滚，需为历史版本预留磁盘。两个包都发生变化且有跨版本依赖时，先在维护窗口验证配套组合，可在节点同一目录解压两个包，一次执行升级。

新镜像通过节点验收后，配套 `tomd` 逐台排空既有电脑的旧会话。节点核对原容器和磁盘身份，关闭原容器，在原磁盘上启动使用新镜像的下一代容器。新容器通过实际探针后，服务端提交新镜像、代次和容器 ID，聊天与 Agent 随后使用新实例。`control_started` 表示节点控制服务启动，既有电脑的完成日志为「已有电脑已切换到验收通过的新镜像」，按电脑 ID 和新代次核对。

电脑迁移需要先部署配套 `tomd`，服务端启动时向前应用迁移 `0080`。迁移期间未获执行资源的工作等待电脑恢复。旧会话清理或新实例验收无法确认时，保留原磁盘和迁移记录，停止为该电脑签发会话。旧计划完成后才会安装下一轮发布镜像。中断后继续原计划。已切换的电脑使用向前修复处理后续故障，禁止手工切换磁盘或回填旧代次。

### 按组件选择维护范围

先升级配套的 `tomd`，等它完成迁移 `0087` 再下发节点程序包。该迁移在维护记录和远程作业上增加可空阶段字段，建立宿主修复的重核记录及诊断函数。现有业务行无需回填，建表和增加列需要短暂的数据库元数据锁。控制端降级前须排空新协议的维护窗口，并使用服务端升级前的成套数据库和程序备份。

在独立程序包目录执行 `sudo ./tomnode upgrade`。安装器先核对清单、已安装的组件摘要、原身份和未完成的本地升级记录。

| 变化 | 节点实际动作 | 成功回执 |
| --- | --- | --- |
| 仅 bot-agent | 原子切换 Bot 入口。运行中的进程使用原程序，新进程使用新程序。 | `program_applied`，范围 `bot` |
| 仅 tomnode，或 tomnode 与 bot-agent 同时变化 | 申请绑定原镜像、操作 ID 和发布摘要的维护窗口。核对会话、验收租约和电脑切换后替换宿主程序；混合更新同步切换 Bot 入口。 | `control_started`，范围 `host` 或 `host_bot` |
| 电脑基础程序、镜像或服务布局 | 使用完整维护流程，先处理有冲突的在途电脑计划。镜像变化时逐台切换原电脑。 | `control_started`，经历电脑恢复的操作返回 `computer_ready` |
| 同一组程序重复下发 | 核对本机文件和 Bot 入口，复用当前版本。 | `program_applied`，范围 `unchanged` |

宿主维护允许原电脑计划停在尚未领取的排空阶段。活动会话、未交还的验收或电脑租约、已开始切换的实例、状态不明的操作都会阻止停机。节点能力验收处于隔离时仍可安装符合这些条件的宿主修复。新版启动后，控制端只对已知的 `agent_retirement_entry_unknown` 退役故障重新核对原验收资源。同一资源围栏和修复发布只领取一次。验收通过后后台继续领取原电脑迁移。

CLI 输出当前步骤、操作 ID 和阻塞原因。管理平台的“电脑节点 → 详情”显示当前维护或电脑迁移步骤，“远程升级”显示作业的下载、检查、切换和失败阶段。`verification_quarantined/agent_retirement_entry_unknown` 表示领取电脑迁移之前，节点的临时验收资源已被隔离。`active_session` 表示有会话尚未结束。宿主启动与用户电脑恢复分别确认。

中断后在同一程序包目录重跑原命令。节点校验已提交文件与启动记录，复用原操作 ID；只有交还维护的回执丢失时不会再次停止服务。仅宿主或宿主加 Bot 更新时，新服务启动明确失败会自动恢复原二进制、安装快照和 Bot 入口，验收旧服务后交还窗口。原服务也启动失败时保留回滚记录和维护窗口，重跑同一命令会续接回滚。程序包和镜像不兼容时须按成套备份的流程恢复。

若程序已经升级，现有用户电脑仍因历史错误被隔离，在**已安装版本的独立程序包目录**执行 `sudo ./tomnode upgrade --recover-computers`。安装器按原规格、容器 ID、代次和围栏验证恢复证明。对于 `container_stop_unconfirmed`，还会确认原容器已退出、PID 为零、没有自动重启策略。未确认的资源继续隔离。已有回执被打断时优先续接原命令。首次拆分安装仍需配套镜像包。

**恢复与回滚。** 失败查看节点日志 `journalctl -u tombot-node-update -u tombot-node -n 100 --no-pager`。升级阶段不明时保留维护状态和修复计划；恢复连接后下发同一版本。完成回执先在节点落盘，重发回执不会再次停服务。需要回退时，重新下发上一份已登记且与当前运行环境匹配的程序包或镜像包。首次拆分若要回到内置代理的旧镜像，先排空，再恢复首次切换前成套备份。不能只回退宿主二进制，或回退到无法交还维护窗口的版本。旧版管理平台回滚前须使所有已领取任务完成并停止更新定时器，按服务端配套备份恢复数据库，不能编辑历史迁移或删除节点身份。

**存储与部署。** 服务端在 `/var/lib/tombot-node-releases` 保存核验后的归档，每个管理员最多保留一个待完成归档。单包上限 17 GiB，传输分片 4 MiB。多实例须共享支持文件锁和原子重命名的持久卷。为暂存、归档、节点备份和镜像预留空间。回退到旧协议时恢复迁移前数据库、升级缓存、配套程序、systemd 单元及旧协议所需配置。
