# TomBot 多用户服务发布包

本包统一交付 Linux amd64、arm64 宿主程序、管理平台、systemd 单元、部署格式及专用电脑镜像构建上下文。所有组件来自同一份工作树源码快照，包含未提交的当前改动；不把 Git 提交号当作脏工作树的完整来源。包内不包含数据库连接、模型凭据、登录材料、TLS 私钥或业务数据。

发布包完整不代表电脑能力或生产环境已经验收。当前共享浏览器联合探针尚未完成，完整节点验收仍会阻止开户。公开远程电脑交互继续暂缓。

## 构建与核验

在源码仓库的 `server/` 目录执行：

```sh
make lint check test
make release RELEASE_ARGS='--version 0.2.0-rc.1 --output /绝对路径/tombot-0.2.0-rc.1.tar.gz'
make verify-release RELEASE_VERIFY_ARGS='--archive /绝对路径/tombot-0.2.0-rc.1.tar.gz --sha256 发布渠道提供的完整摘要'
```

输出父目录必须存在，目标文件必须不存在。版本必须是明确的三段数字，可带小写预发布后缀。构建器复制已声明的源码输入到私有临时目录，在该快照中运行锁文件约束的 `npm ci`、管理端类型检查及 Vite 构建，并编译全部 Linux 程序；不会复用原工作树中的 `admin/dist` 或旧二进制。Go 使用本机工具链、只读模块清单、关闭 VCS 自动标记和路径修剪；工具链版本必须满足 `go.mod`。构建不自动安装 Go、Node.js 或 Docker。

源码摘要包括文件相对路径及内容，不含修改时间。构建完成后再次检查快照未被构建步骤改写。程序架构、必要组件、文件权限、内容摘要、管理端路径与容量都在打包及只读复验中检查。归档使用规范 USTAR 和零时间戳 gzip；对同一输入及工具链，归档不因打包时间和临时目录变化而改变。依赖和工具链的构建差异仍可能改变二进制，不能只凭版本字符串断言相同内容。

构建器不输出软件源、环境及外部工具的原始内容，只报告当前阶段和失败退出码。npm 安装最多 10 分钟，前端构建及每个程序编译最多 5 分钟；超时或取消会终止该步骤的进程组。构建、打包或核验失败不发布成品；通过后原子创建最终文件，拒绝覆盖任何同名文件。目录刷盘失败会明确报错；若目标已出现，应保留并以原摘要重新核验，不自动删除或覆盖未知发布结果。

最终 JSON 回执中的 `scope: release_artifacts` 只表示发布产物完整；`sha256` 是整个压缩包的摘要，`source_sha256` 是源码快照摘要。应通过受信发布渠道另行分发整个包的摘要。包内清单自带的散列不能证明发布者身份；只读核验要求显式提供外部摘要，不以“从待验包重新计算一个摘要”替代来源确认。核验不解压、不安装、不启动服务，拒绝重复路径、附加文件、链接、扩展头、错误权限、架构错误、缺失组件和超限内容。

包内 `tools/release_bundle.py` 和其依赖支持在没有源码仓库的部署机上执行同一 `verify` 命令。使用它们之前，先用系统 SHA-256 工具将压缩包与受信渠道的摘要比对，再向空目录解包；不要先运行来源未确认的包内程序。包内工具只用于核验，构建仍从完整源码仓库执行。

## 目录与安装映射

| 包内路径 | 用途与部署位置 |
| --- | --- |
| `manifest.json` | 格式版本 3，平台、源码摘要及全部文件的 SHA-256、大小和权限 |
| `linux-<架构>/bin/tomd` | 非 root API/Worker，安装到 `/usr/local/bin/tomd` |
| `linux-<架构>/bin/tomnode`、`tomdeploy-config`、`tomdeploy-check`、`tomdocker-bootstrap`、`tomimage-prepare` | root 节点、配置生成、安装前检查及引导，安装到 `/usr/lib/tombot/` |
| `linux-<架构>/bin/tomdb`、`tomnode-register` | 独立数据库迁移与节点登记命令，安装到 `/usr/local/bin/` |
| `linux-<架构>/computer-image/` | 自包含的对应架构 Docker 构建上下文，含四个容器内程序；不安装到宿主命令路径 |
| `admin/` | 已构建的同源管理平台，复制到 `/opt/tombot/admin` 并在 `server.json` 指定该目录 |
| `deploy/tomd.service`、`deploy/systemd/*.service` | 安装到 `/etc/systemd/system/` 的系统服务定义 |
| `deploy/*.schema.json`、`deploy/node.example.json` | 清单格式与节点配置参考；不作为可直接启动的生产配置 |
| `deploy/CONFIGURE.md` | 单份部署参数生成五份一致配置的调用及参数说明 |
| `tools/` | Python 只读核验工具及其依赖；不安装为系统服务 |

核验后只向新建空目录解包；核验器不为通用解包器提供任意目录写权限。安装宿主程序前核对实际 CPU 架构。宿主程序和服务单元由 root 管理，分别使用 0755、0644 权限；宿主引导支持 Ubuntu 24.04、systemd、cgroup v2，容器系统仍是 Debian 13。

电脑上下文可直接作为 Docker 构建目录。构建后运行源码中的专用镜像验收，推送到部署指定仓库并记录实际摘要，再生成 `computer-image.json`。不能把本地标签、上下文打包成功或任意测试镜像 ID 写成已验收的生产镜像。镜像部署清单、Docker/宿主包受测版本清单都属于具体部署环境，发布包没有自动填入示例版本。

## 首次部署顺序

1. 准备新 PostgreSQL 数据库和四个最小运行角色、独立迁移身份、固定非 root 的 `tombot-api` 用户及 UID/GID、TLS 和加密文件、用户磁盘存储及备份目标。API 不加入 Docker 组。
2. 安装同一发布包的程序、管理端和服务单元。按包内 `deploy/CONFIGURE.md` 准备一份非秘密部署参数，使用 `tomdeploy-config` 生成服务、节点、Docker、镜像与节点登记配置到全新目录；审阅后成套安装到 `/etc/tombot/`。节点与 API 的控制通道身份由双方证书指纹固定（部署参数 `control`），不再绑定 API UID/GID；覆盖参数仍须满足目录与时限约束。配置引用独立受保护文件；不要把凭据放入命令行、版本库或日志。
3. 通过独立迁移身份执行 `tomdb`；日常 API 只验证迁移账本。通过 API 身份执行不带参数的 `tomnode-register`，用 `TOM_SERVER_CONFIG` 和 `TOM_NODE_REGISTRATION_REQUEST` 指定受保护配置及操作文件；操作文件中的 `action: register` 登记节点和固定摘要镜像，`action: status` 查询原登记。不得手改 `ready`。
4. 启动 `tomd.service`，由 systemd 依次执行成套配置检查、Docker 和宿主工具引导、固定镜像准备、受信节点。检查程序复用四份实际配置，核对身份、时限、目录及引用文件的权限，失败时不会开始本次自动安装。API 的 `Wants` 依赖允许节点故障时继续提供登录和历史查询；配置检查与节点控制就绪均不代表电脑验收通过。
5. 打开管理站点 `/admin/`。平台还没有管理员时，登录页提供“创建首位管理员”入口，由部署者当场设定用户名、显示名称与初始密码，并一次性显示动态验证器密钥。之后的管理员由已登录管理员在“管理员”页创建。登记节点与镜像可在“电脑节点”页完成，或继续使用 `tomnode-register`。共享浏览器等任何必要能力未确认时，普通用户开户仍停在此门槛，不能绕过。
6. 完成多用户/多 Bot、实际挂载配额与进程回收、共享浏览器、故障恢复及一致性备份恢复验收后，再对外切换流量。

本包不自动创建宿主用户或数据库角色，不生成生产凭据，不安装系统服务，也不宣告首次部署验收通过。已提供配置生成入口；受测宿主清单及真实 Ubuntu 首次安装联调仍属于生产部署剩余工作。

安装前检查的账户、路径、权限及失败语义见源码中的 `docs/deployment-check.md`。API 配置应由 root 管理并允许 API 读取，私有引用由 API 身份读取；其他三份配置保持 root 私有。节点示例最大租约为 5 分钟，覆盖默认 3 分钟节点验收。检查命令不读取凭据内容，也不会为缺失的配置生成默认成功结果。

## 兼容性、升级与回滚

`make release` 由分散交叉编译文件改为单个完整双架构压缩包，不再生成旧 `bin/tomd-linux-*` 布局；调用者使用上表路径。没有旧布局兼容层，开发用 `make build` 保留本机编译用途。

格式版本 3 在配置检查基础上增加必需的双架构 `tomdeploy-config` 和参数说明；新核验器拒绝格式 1、2，不允许遗漏程序或仅更新服务依赖。成套升级五个 systemd 单元，重新加载并启动依赖链。该发布格式变化不修改数据库或节点记录。

发布更新必须作为完整集合评估，不能只替换 API 而保留不匹配的节点、电脑程序或管理端。停止接单、排空执行、共享浏览器与出网，保存 PostgreSQL、密钥文件、用户磁盘、节点最高代次与关闭屏障的一致恢复点，然后切换到同一发布包的组件。当前生命周期记录版本 4、存储记录版本 3、镜像存储布局版本 2，每桌面会话记录版本 2；旧记录不自动迁入。历史 SQL 迁移保持不可变，通过新增迁移前向更新。

共享浏览器监督引入代理 `config.json` 版本 4 与 `browser.json` 版本 1，节点与镜像须配套更新。旧配置不原地改写；旧代理不能接管新控制目录，回滚不能删除消费版本或未关闭记录。宿主浏览器生命周期已接入节点，完整生产验收尚未完成；本地开发包 `0.2.0-dev.20261112.4` 不包含此后新增监督实现，不能将该包与最新源码生成的配置或镜像混用。

镜像必须带有 `io.tombot.computer.storage-layout=2`。同一用户磁盘的 `workspace`、`browser` 子目录分别挂载到 `/workspace`、`/var/lib/tombot-browser`；升级节点同时更换匹配镜像，不能只改标签让旧镜像通过检查。旧整卷布局不原地转换，开发环境先使用原组件排空和关闭，再建立新的空环境。回滚旧组件只能恢复原环境快照，不能让其读取新存储记录或直接挂载新盘根目录。

回滚必须选择理解当前数据库和节点记录的配套版本；不能删除记录、退回迁移或让旧单用户程序连接新数据库、复用用户卷。新旧系统需要保留时分别部署。实际整套备份恢复和升级回滚演练仍待最终验收，产物完整核验不能替代这些证据。

节点共享浏览器配置要求 `node.json` 版本 2 与必填 `browser` 预算；用户生命周期记录版本 4、宿主 `<user_id>.browser.json` 版本 1 保留跨容器代次最高消费版本。生成配置使用更新后的部署示例，代理预算须与浏览器调用和回收预算匹配。本次不迁移旧状态；回滚先停止接单、排空浏览器和所有 Bot、保留用户磁盘及完整屏障，再恢复整套匹配环境。不能只回滚到会忽略浏览器记录的节点，也不能通过删除记录重新编号。

代理接入等待新增必填 `agent_startup` 预算和无副作用的 `health` 控制动作；节点配置仍为版本 2，代理配置仍为版本 4，不改变持久状态或 SQL 结构。节点、包含该动作的镜像、镜像固定摘要及生成配置必须成套更新；旧代理即使能够监听也不能通过新节点的控制检查。回滚应先排空，再恢复匹配的整套程序、配置和镜像；不得关闭检查或忽略未知响应。共享浏览器文件交互和完整能力探针仍未接通，新增控制检查不能用于开放账户就绪门禁。

会话窗口入口已接入代理资源回收，只有原共享 Chrome 活动时才允许创建 Bot 会话。停服先完成桌面页面与探针回收，再关闭共享浏览器；代理 `shutdown_timeout_ms` 至少覆盖 `call_timeout_ms + 2 × cleanup_timeout_ms`，预算不足的配置明确拒绝。此项不新增 SQL 或持久记录版本；升级和回滚均须停单排空，使用匹配的节点、镜像和预算配置，不能保留旧窗口进程接管新实例。文件交互和完整浏览器探针仍待接通，当前本地镜像不能当作完整生产验收。

根据最新产品要求，自研 GTK 浏览器窗口客户端、Python 包及额外依赖已删除，桌面启动回到真实 XFCE/RFB 就绪与进程监督。远程电脑后续提供原生 Chrome、终端和文件管理器的直接操作；原生 Chrome 的共享账号与独立桌面组合尚未验收。本次没有 SQL 或持久记录版本变更，必须停单排空后成套切换代理与镜像。旧 `window-client-verified-20261112` 镜像仍包含已取消方案，只保留历史验证用途；旧开发发布包也未更新，不得把它们当成当前目标的交付产物。

本地浏览器接口现使用 `/v2`，旧 `/v1` 路由拒绝；窗口增加 `command_state`，等待对话框的成功回包不表示动作已完成。节点 `browser.limits.dialog_timeout_ms` 为必填的累计等待预算，范围 1000–600000，示例为 300000。节点、代理、镜像和本地调用方必须成套更新；旧代理不能读取含此字段的新授权，新代理也不接受缺少预算的旧授权记录，不添加隐式默认值或兼容转换。数据库迁移与记录版本号未改变，但不能据此混用两套程序。

阶段环境先用原版本停止接单并排空，保存用户磁盘、数据库及完整控制记录，再建立使用新配置的配套环境；按项目约定不迁移旧实现的数据。回滚恢复原组件、原配置、原镜像和一致快照，不能删除最高代次或关闭屏障来绕过校验。浏览器执行的最终方向是容器内 Agent 本地调用 Chrome；服务端登记与结果确认已接入协议 3，不新增浏览器逐动作节点 RPC，也不能据此开放生产就绪。


Agent 私有标准流升级为协议 3，增加本地工具授权、结果确认和有界图片分块；协议 1、2 均拒绝。服务端注册 `computer_browser`，容器内 Agent 执行，Unix 网关改为核验当前执行会话的 `shell` 子组。每次本地操作增加登记和持久确认的往返，但 Chrome 动作不经过服务端或节点；每次工具至多读取一次所属窗口列表，列表最多 32 项。截图单次暂存不超过 4 MiB，图片和操作回执原子保存；无 SQL 或持久记录结构变更。

升级须停止接单、排空原 Agent 与会话，使用同一版本的服务端、节点、电脑代理和新镜像重建阶段环境；不要让协议 3 服务端调度旧 Agent。按项目约定不提供旧数据迁移。回滚先排空新运行并保留完整记录，再恢复原组件、镜像、配置与一致快照；不能降协议继续处理未确认动作。本地构建和单项验证不能替代首次安装、开户、cgroup、备份恢复与发布验收。
