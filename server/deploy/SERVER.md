# 服务端一键安装、升级与状态检查

`tomd` 已内置管理平台、数据库迁移、服务单元与安装逻辑。默认安装面向 Ubuntu 24.04 的 x64/arm64 systemd 主机，自动准备本机 PostgreSQL 16；需要访问系统软件源。电脑节点独立安装，管理平台首次登录无需节点就绪。

## 首次安装

将对应架构的 `tomd` 放到当前用户拥有、不可被其他用户写入的目录，不从公共临时目录或符号链接启动：

```sh
chmod +x ./tomd
sudo ./tomd install
```

按提示确认浏览器和电脑节点均可访问的 HTTPS 地址。程序建议本机网卡地址和 9443 端口；公网 NAT 或多网卡主机应填写实际可达地址。也可以跳过交互：

```sh
sudo ./tomd install --url https://你的域名:9443
```

地址不带 `/admin/`、查询参数或结尾斜杠。直连端口范围 1024–65535，省略端口使用 9443。安装器不更改防火墙或云安全组，部署网络须允许管理端和节点访问该端口。

自动完成：

1. 创建专用非 root 账户 `tombot-api`，不加入 Docker 组。
2. 生成 HTTPS 服务证书、节点调用客户端证书、三份独立 32 字节应用密钥，以及五份独立数据库连接文件。
3. 安装 PostgreSQL 16，创建 `tombot` 数据库、独立迁移身份、四个 `NOLOGIN` 权限组及各自的业务登录身份。密码随机生成，仅保存到私有文件；业务身份不获得超级用户或绕过行级隔离的权限。
4. 安装当前二进制、服务配置和 systemd 单元，设置开机启动。
5. 启动 `tomd` 自动迁移数据库，使用实际证书验证本机 HTTPS API 和四个数据库连接的健康状态。

安装完成后访问输出的 `/admin/` 地址，创建首位管理员并绑定动态验证器。没有默认管理员或默认密码。

自动 HTTPS 证书使用浏览器支持的 ECDSA P-256，有效期一年，是自签名证书。访问设备需要信任 `tomd status` 输出的公共证书文件，首次安装为 `/etc/tombot/server/certificate.pem`。安装器不自动申请公网证书，也不自动续期。已有正式 HTTPS 证书时：

```sh
chmod 600 ./privkey.pem
sudo ./tomd install --url https://你的域名:9443 \
  --certificate ./fullchain.pem --private-key ./privkey.pem
```

证书必须匹配访问域名或 IP、处于有效期内；私钥须未加密且仅所有者可读写。安装器复制它们，不依赖原始上传目录继续存在。

## 安装失败与重试

若在证书生成阶段失败，配置与数据库尚未发布，可修正原因后重新执行首次安装命令（含 `--url`）。错误会标明 HTTPS 服务身份或节点通信客户端身份，并保留证书库的具体原因；排查时提供错误日志即可，不要提供私钥或数据库连接文件。

配置已发布后，再次执行同一程序，不再提供首次参数：

```sh
sudo ./tomd install
```

已发布的证书、密钥和数据库身份会保留；安装锁避免并发运行。数据库角色创建使用事务和安装标识，重试不重置密码，不接管同名数据库或角色。未完成的服务启动可重试，并重新检查实际健康状态。

首次启动直接启用服务；仅当 `tomd.service` 处于失败状态时，才清除失败与启动限流。服务管理命令失败时会显示具体操作和单元名称。若旧版在程序和服务单元安装完成后、首次启动前中断，可用修复版执行 `upgrade`，备份并沿用已有配置及数据库完成启动，不必删除安装目录或重新生成身份。

已有 `/etc/tombot/server.json`、`/usr/local/bin/tomd`、`tomd.service` 或安装目录却没有匹配记录时明确拒绝，不覆盖人工部署。系统包管理器被强制中断、磁盘损坏或已有数据库认证规则不适配时会报告失败，不关闭检查或改写宿主认证规则。

## 升级

将新版本下载到另一个受保护路径，用**新程序**执行：

```sh
chmod +x ./tomd-new
sudo ./tomd-new upgrade
```

升级器不联网决定版本，不下载或执行远端脚本。它会先核验配置、安装归属及候选程序支持的数据库迁移账本，然后：

1. 停止当前服务，确认进程已退出。正在运行的任务按现有服务退出流程取消并保存恢复记录，升级会短暂停机。
2. 在 `/var/lib/tombot-server/backups/` 创建权限为 `0700` 的备份目录，保存数据库自定义格式导出、配置、所有引用的证书和密钥、原程序、服务单元及安装记录；清单记录文件原路径、权限、身份和 SHA-256。
3. 本机托管数据库通过本机 `postgres` 身份导出，完整包含启用强制行级隔离的租户数据；四个业务身份不提权。
4. 核验备份完整性，原子替换程序和服务单元，保留运行配置、数据库凭据和应用密钥。
5. 启动新服务，自动迁移并检查健康；成功后输出备份路径。

重复执行同一已安装版本只做检查。升级中断后继续用同一新版程序执行 `upgrade`，复用阶段记录及原备份。即使期间机器重启，也会先停止可能自动启动的旧进程。备份失败不会替换程序；备份损坏会阻止继续升级；不同候选程序不能覆盖尚未完成的升级记录。

旧版自动生成的 Ed25519 HTTPS 证书会使 Chromium 报 `ERR_SSL_VERSION_OR_CIPHER_MISMATCH`，即使 Go 客户端的健康检查成功。修复时使用：

```sh
sudo ./tomd-new upgrade --renew-https
```

该参数仅替换自签名 HTTPS 服务身份，不接管证书机构签发的证书。升级先备份原证书和配置，再将新的成对证书文件发布到独立目录，原子切换配置引用；中断重试复用同一新证书。应用加密密钥、数据库身份及节点调用客户端身份继续沿用。普通 `upgrade` 不重新签发证书。

重新签发会改变 HTTPS 证书指纹。完成后按 `tomd status` 输出的公共证书位置和 SHA-256 指纹重新建立浏览器信任；已固定旧服务证书指纹的节点也需更新信任配置。原证书仍保留在原路径及升级备份中，回滚时恢复备份配置即可恢复原 HTTPS 引用；如果升级同时改变了数据库结构，仍按下文的完整回滚流程恢复数据库。

备份可能很大，需预留数据库导出与程序、配置的空间。备份包含数据库连接与解密材料，不应公开或提交仓库。升级器只协调本机单个服务；共享同一数据库的其他 API 实例必须提前停单排空。电脑节点用户磁盘由节点维护，服务端升级备份不替代数据库和用户磁盘的整套灾难恢复备份。

## 状态与日志

```sh
sudo tomd status
sudo journalctl -u tomd -n 100 --no-pager
sudo journalctl -u tomd -f
```

`status` 不安装软件、不修改配置或启动服务，只短暂取得部署互斥锁。它检查安装归属、程序及单元摘要、证书、文件权限、systemd 活动与开机启动状态、API/数据库就绪状态；未安装、服务停止或健康异常返回非零退出码。该健康结果不表示电脑节点或模型供应商就绪。

## 文件位置与高级配置

| 位置 | 用途 |
| --- | --- |
| `/usr/local/bin/tomd` | 程序，root 0755 |
| `/etc/systemd/system/tomd.service` | 系统服务，root 0644 |
| `/etc/tombot/server.json` | 实际运行配置，root 0644，升级保留 |
| `/etc/tombot/server/` | 证书与密钥目录，root 0755；私钥、密钥、连接文件为服务账户 0600 |
| `/etc/tombot/server/installation.json` | root 0600 安装记录及首次配置快照，仅用于安装恢复，不是运行配置 |
| `/etc/tombot/server/upgrade.json` | 未完成升级的 root 0600 阶段记录，成功后删除 |
| `/var/lib/tombot-server/backups/` | root 私有升级备份 |

常规运行仍以非 root 身份执行 `tomd`，通过 `TOM_SERVER_CONFIG` 读取配置；安装、升级和完整状态检查才使用 root。修改运行参数后执行 `sudo systemctl restart tomd`。不要为升级重新生成应用密钥。

已有外部 PostgreSQL 或自定义配置时，可在新部署上使用：

```sh
sudo ./tomd install --config ./server.json
```

此模式沿用[服务配置契约](../internal/serverapp/README.md)，必须事先准备证书、密钥和五份数据库连接文件，并使 `tombot-api` 可以读取。安装器会复制配置，不创建数据库、角色或密钥，也不会接管已有人工安装。远程数据库连接必须启用 TLS。不能与 `--url`、`--certificate`、`--private-key` 混用。

高级模式升级需要本机已有与数据库匹配的 `pg_dump`。迁移连接须使用带主机和独立登录密码的 PostgreSQL URI，且该身份应具备完整备份所需权限，包括导出强制行级隔离的表；不得为此提升四个业务身份的权限。备份口令通过临时私有文件提供，不进入命令参数或环境变量值，完成后删除。

## 迁移与回滚

本功能不新增或修改业务 SQL 迁移。安装只准备数据库与角色，业务结构继续由 `tomd` 内嵌的不可变迁移链处理。现有人工部署可继续通过原 `TOM_SERVER_CONFIG` 运行；安装器不会隐式转换或覆盖它，采用自动安装应在独立环境验证后切换。

新服务启动失败时，数据库迁移可能已经提交，因此升级器保留新程序、原备份和阶段记录，不自动恢复旧二进制。通常修复原因后重跑同一新版的 `upgrade`。如需回滚，先停服务，并依据备份 `files.json` 恢复原配置、证书、密钥、程序、单元及安装记录；数据库版本变化时还必须用 `pg_restore` 在维护窗口恢复到配套空数据库，再重新加载 systemd 并验证。确认已完整恢复后处理原未完成升级记录，不能仅删除记录或降迁移账本来绕过失败。正式恢复须同时评估节点磁盘及升级后新增数据。

当前自动化验证包含隔离文件系统下的首次安装、重复和失败恢复、冲突与锁、升级备份及中断重试、真实 HTTPS 校验、真实 PostgreSQL SCRAM 认证、迁移权限和账本检查、包含租户数据的导出恢复。软件源安装与 systemd 宿主生命周期仍需在目标 Ubuntu 主机验收。
