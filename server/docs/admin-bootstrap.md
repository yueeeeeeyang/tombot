# 首位管理员创建

首位管理员在管理站点登录页创建，不再需要本机命令。管理员与普通用户是两套独立身份：管理员只做平台管理，不持有用户电脑，也不登录桌面客户端，因此账号创建后立即生效，不进入用户开户工作池。

登录页只在平台还没有任何管理员时显示“创建首位管理员”按钮，该判断来自公开只读接口 `GET /api/v2/auth/admin-setup`，它只返回一个布尔值，不透露管理员数量、用户名或状态。已有管理员后按钮消失，后续账号由已登录管理员在“管理员”页创建。

[节点与镜像目录登记](node-registration.md)仍提供独立部署命令，管理平台的“电脑节点”页也可以登记同一份目录；登记不会标为就绪，就绪仍取决于心跳、部署检查与真实能力验收。当前不能据此宣告新机器部署完成，特别是浏览器未就绪时，不能手工写入就绪状态或使用测试探针开放账户。

## 前置

1. 使用 `tomdb` 在全新 PostgreSQL 初始化全部迁移，按[应用配置](../internal/serverapp/README.md)准备四种用途的连接文件。历史迁移不改写。
2. 配套节点通过 Docker 引导、存储和资源检查，登记实际节点与固定镜像。API 以独立非 root 身份运行，不加入 Docker 组。
3. 启动 `tomd`。管理员创建不依赖节点或电脑供给，节点未就绪时仍可创建管理员并登录平台。
4. 打开部署配置的 HTTPS 管理站点 `/admin/`。

## 创建流程

登录页出现“创建首位管理员”时，填写管理员用户名、显示名称与初始密码（至少 12 个字符，需二次确认）。提交后服务端在单个事务内：

1. 取得 `tombot.bootstrap.administrators` 咨询锁并确认 `tombot.administrators` 为空，避免并发建出两个首位管理员；
2. 写入状态为 `active` 的管理员账号与口令散列；
3. 生成 20 字节动态验证器密钥，用服务端主密钥加密后保存，只把 base32 编码的密钥返回一次。

页面随即展示验证器设置密钥：在验证器中手动添加时间型账户，名称填写管理员用户名，输入该密钥，使用每 30 秒更新的 6 位 SHA-1 动态码。关闭页面后无法再次查看该密钥；丢失只能由其他管理员重建账号。

随后使用用户名、初始密码和验证器动态码登录。登录不创建隐式会话之外的任何凭据；会话访问凭据到期前由页面自动续期，无需手动操作。

平台已存在管理员时，该接口返回 `409 ADMINISTRATOR_CONFLICT`，不会静默创建第二个初始账号。

## 后续管理员

已登录管理员在“管理员”页点击“创建管理员”，填写用户名、显示名称与初始密码。创建需要近期二次验证；若验证窗口已过期，页面会弹出验证框，通过后自动继续刚才的创建，不需要重新填写表单。

创建成功后一次性展示该账号的验证器设置密钥，同样只显示一次。管理员账号不分配电脑，也不出现在桌面客户端。

## 故障与恢复

创建是单个数据库事务：事务已提交而响应不确定时，用刚设置的凭据尝试登录核实；事务未提交时重新提交即可。不要为了绕过结果不确定而改用旧激活材料——管理员激活材料已随 `0051_administrator_direct_setup.sql` 移除。

`0051` 同时把历史上处于 `pending_activation` 的管理员统一改为 `disabled`，因为旧激活流程已不存在。这类账号无法登录，需由其他管理员重建；平台在他们之外必须仍保留至少一名有效管理员，否则最后管理员保护会阻止该更新。

## 验证覆盖

真实 PostgreSQL 测试覆盖首位管理员创建、唯一性冲突、验证器密钥加密保存、错误主密钥无法解密验证材料、管理员登录防重放、再验证窗口过期返回 `VERIFICATION_REQUIRED` 以及最后管理员保护。部署签发的材料还通过正式 HTTPS 应用完成登记、首次登录与管理接口访问，核对无隐式登录、Cookie 属性及管理会话值不返回页面。

前端检查覆盖首建表单的密码确认、错误协议拒绝、验证器密钥一次性展示、登录页入口按管理员存在与否显示，以及敏感操作在再验证后自动重试原请求。
