# 首位管理员部署入口

`tomadmin-bootstrap` 是生产部署链路中的本机命令。它复用与 `tomd` 相同的账户状态机，首位管理员必须同步获得已通过真实检查的电脑，才能签发激活材料。命令不建立默认账号，不跳过电脑供给，不注册管理 HTTP 旁路。

本入口已实现创建、状态查询、失败重试、隔离资源对账和激活材料交付，管理平台也已接通验证器登记、激活和返回登录。[节点与镜像目录登记](node-registration.md)已提供独立部署命令，但登记不会标为就绪；生产部署阶段还须接通独立节点、镜像准备与实际能力探针。当前不能据此宣告新机器部署完成，特别是浏览器未就绪时，不能手工写入就绪状态或使用测试探针开放账户。

## 前置与调用

1. 使用 `tomdb` 在全新 PostgreSQL 初始化全部迁移，按[应用配置](../internal/serverapp/README.md)准备四种用途的连接文件。历史迁移不改写。
2. 配套节点通过 Docker 引导、存储和资源检查，登记实际节点与固定镜像。API 以独立非 root 身份运行，不加入 Docker 组。
3. 启动 `tomd` 及其开户工作池。部署命令不另起 Worker，不启动模型执行，不直接控制 Docker。没有工作池时，开户保留为待处理，命令有界等待后明确返回未完成。
4. 使用与 API 相同的 Linux 身份调用命令。`TOM_SERVER_CONFIG` 指向相同服务配置，`TOM_ADMIN_BOOTSTRAP_REQUEST` 指向本次操作 JSON；不接受命令参数。文件路径必须规范且绝对，文件由 root 或服务身份持有，不可被其他身份写入。

```sh
# 在已切换为 API 服务身份的部署会话中执行；这里只指定文件路径。
TOM_SERVER_CONFIG=/etc/tombot/server.json \
TOM_ADMIN_BOOTSTRAP_REQUEST=/etc/tombot/bootstrap-request.json \
/usr/lib/tombot/tomadmin-bootstrap
```

构建入口 `make build` 与 `make release` 均包含此命令；发布时安装匹配架构的二进制。命令核对四种连接属于同一数据库，仅打开控制角色连接并验证完整迁移账本。它不读取模型或身份加密文件，不使用迁移账户。

## 操作文件

以下仅为字段说明。节点及镜像标识必须替换为部署实际登记值，资源额度须在宿主验收的档位内。幂等键在首次执行前确定并保存，网络中断或命令重启后保留原值与原开户字段。

```json
{
  "action": "create",
  "create": {
    "username": "platform-admin",
    "display_name": "平台管理员",
    "node_id": "部署登记的节点 ULID",
    "image_id": "部署登记的镜像 ULID",
    "resources": {
      "cpu_millis": 2000,
      "memory_bytes": 4294967296,
      "disk_bytes": 21474836480,
      "process_limit": 512
    },
    "idempotency_key": "initial-administrator"
  }
}
```

角色固定为管理员；不提供 `role`、`request_id`、密码或其他认证材料。请求中的节点必须与服务配置一致。请求取消只停止本次等待，不撤销数据库中已受理的开户。

普通回执包含 `action` 和 `operation`，后者含 `id`、用户、电脑、状态、阶段和尝试次数，不含认证材料。创建等待超时仍输出原操作并以非零状态退出；后续使用 `status` 查询，不能把输出 JSON 的存在当作创建成功。

| 动作 | 附加字段 | 行为 |
| --- | --- | --- |
| `status` | `operation_id` | 查询首次引导产生的管理员操作；不接受普通用户开户标识 |
| `retry` | `operation_id` | 仅对已确认清理完成的失败开户重试，保持原用户、电脑和操作标识 |
| `reconcile` | `operation_id` | 只对隔离的首次开户做资源清理对账，不直接重建；清理确认后另行重试 |
| `activation` | `operation_id`、`activation_file` | 对电脑已就绪且尚未激活的首位管理员签发材料 |

例如查询文件仅包含：

```json
{"action":"status","operation_id":"创建回执中的操作 ULID"}
```

`status` 成功只表示查询完成；必须检查返回的操作状态。`reconcile` 成功且操作为 `failed` 表示清理完成、账户仍未开通，并非电脑创建成功。所有动作拒绝未知字段、尾随内容及混合操作参数。

## 激活材料交付

由部署预先准备 API 身份拥有、权限为 `0700` 的专用目录，`activation_file` 指向其中尚不存在的文件。命令先以 `0600` 独占创建输出，再签发激活材料；不会覆盖现有文件、跟随末级符号链接或向终端、日志输出材料。

文件保存用户标识、一次性激活值与到期时间；写入和目录均刷盘，文件身份及权限复验成功后，普通回执才标记 `activation_saved: true`。失败清理只删除本次创建且身份未变的文件，替换后的未知文件保留并报错。文件交付失败不会伪装成成功；再次签发必须是显式操作，并会废止之前尚未使用的激活值。

打开部署配置的 HTTPS 管理站点 `/admin/`，点击“激活管理员账户”，粘贴输出文件中 `activation_token` 字段的值。页面验证材料后展示验证器设置：在验证器中手动添加时间型账户，填写管理员用户名与设置密钥，使用每 30 秒更新的 6 位 SHA-1 动态码。设置至少 12 个字符的密码、再次确认密码并输入动态码，即可激活。此流程同样支持管理员为其他待激活管理员签发的材料。

激活成功后页面清除材料并返回登录，不隐式创建会话。等待验证器生成新的动态码，再使用开户时的用户名和新设密码登录；激活时已用的动态码不能重放。提交后断连、超时或响应状态不明确时，页面显示结果待确认，清除材料并引导登录核实，不自动重发激活。明确的验证码错误允许重新输入，过期或已消费材料返回材料输入步骤。

页面只在本次交互内保留材料，离开页面或进入浏览器历史缓存时清除输入并取消在途请求；不写入 URL、本地存储或会话存储。设置密钥默认隐藏，可短暂显示。登记与激活使用固定公开认证路径，不携带管理 Cookie 或 CSRF，不改变其他管理会话；协议见[认证接口](../internal/authapi/README.md)。材料不放入版本库或命令参数，激活完成后按部署机密文件保留策略回收输出文件。

## 故障、迁移与回滚

此入口不修改数据库结构，不新增基础数据迁移。运行时开户和签发仍由账户领域事务写入持久操作、容量和审计。独立命令只能操作首次引导的管理员，不能通过本机请求操作普通用户或建立第二名初始管理员。

进程中断、数据库失联或输出丢失后，保留原操作文件、幂等键和数据库；同参数重发 `create` 或用回执查询，不删除用户记录、电脑卷、租约或关闭屏障。失败仅在已确认清理完成后重试；未知资源先对账。

部署变更包含一个新的 Linux 二进制及操作文件约定，没有改变 API 契约、节点协议或电脑镜像。停用此命令不会取消已经受理的开户，仍由 `tomd` 持久工作池处理。回滚须保留全部操作、激活摘要、审计及配套节点资源，不回退到单用户程序，也不重新签发来掩盖未确认的交付。

测试覆盖严格请求、错误身份、真实 PostgreSQL 的首次开户、幂等、未就绪拒绝激活、普通开户查询拒绝、私有文件交付、链接及路径替换拒绝、失败清理与原激活值保留。部署签发的材料还通过正式 HTTPS 应用完成登记、激活、防重放、首次登录与管理接口访问，核对无隐式登录、Cookie 属性及管理会话值不返回页面。

前端检查覆盖材料校验、密码确认、错误动态码、过期、未知结果、重复提交、取消与迟到响应、历史页面清除及非完成状态拒绝。浏览器验证浅深色、窄屏无横向溢出、键盘焦点和激活到登录流程，使用正式 CSP；截图中的密钥字段额外遮挡。浏览器业务接口及节点资源均使用明确夹具，不代表真实 Docker 供给或生产内核资源验证已完成。
