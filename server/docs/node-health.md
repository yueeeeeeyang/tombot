# 节点控制租约与就绪门禁

节点控制服务能响应、Docker 能工作、固定镜像已准备、用户电脑具备完整能力，是不同证据。`heartbeat` 只证明受保护的节点控制进程当前能响应（跨主机时为已通过证书指纹认证的 HTTPS 端点），不能授予节点或电脑 `ready`。[独立电脑验收与发布流程](node-verification.md)已接通，仍须生产检查和共享浏览器阶段的真实能力证据。

## 数据与进程代次

节点在持有生命周期独占锁后，先原子保存 `node-runtime.json` 版本 1，再继续恢复探针和执行会话。记录固定节点、进程实例 ULID 和跨启动单调递增的代次；构造失败也消费新代次，不能重用。每次启动生成新的实例 ID，单进程心跳序号通过原子操作递增。代次/序号溢出、文件损坏、身份变化、权限或链接异常均失败，不覆盖恢复证据。

节点 API 新增固定 `heartbeat` 动作，只接受 `node_id`，返回节点、进程实例、代次及序号，不返回路径、Docker 权限或能力成功标志。调用方身份由双向 TLS 证书指纹确认，并核对请求标识、动作及归属。它与首次开户的电脑代次是不同概念，不改变用户电脑实例或执行租约。

迁移 `0045_computer_node_control_lease.sql` 为目录新增 `runtime_id`、`control_sequence`、`control_expires_at`；`generation` 表示节点启动代次，`last_seen_at` 保存观察起点。数据库约束和触发器拒绝无租约的就绪、代次或序号倒退、同代次更换实例、删除绑定及用重复序号刷新期限。旧 `ready` 行被前向改为 `bootstrapping`，容量预留、电脑数据、排空状态和身份保留；迁移不会伪造在线证据。

## 观察与一致性

`tomd` 的节点观察服务先用控制连接取得数据库时刻，结束短事务后查询节点，再以独立短事务发布心跳。有效期锚定调用前的数据库时刻；网络耗时、排队和数据库行锁等待不会把旧结果重新计时。保存时先锁定节点行，再读取当前数据库时钟并校验期限，拒绝未来起点、过期结果和旧进程/旧序号。业务事务不跨越节点调用。

多个 API 进程可观察同一节点；节点全局递增序号与数据库行锁共同处理乱序，较晚提交的旧结果不能覆盖新结果。提交结果未知时不重发同一心跳，下一轮进行新的观察。每轮取时、调用和保存各有 `node.call_timeout` 限制；独立观察之间使用 `node.heartbeat_interval`，不存在无限重放同一动作。失败与恢复记录带节点 ID 的中文日志，不记录原始错误内容。

新增配置默认 `heartbeat_interval="10s"`、`control_lifetime="2m"`，沿用 `call_timeout="30s"`。租约必须覆盖三次调用预算加间隔，上限 5 分钟；调用及间隔各限 1 秒至 1 分钟。部署可以显式调整，但不能关闭有效期。数据库时钟是控制租约的时间依据；节点的新旧判定使用持久代次及序号，不依赖客户端墙上时间。

## 失联与恢复

开户、失败重试和管理目录查询共用数据库 `computer_node_status` 规则：排空保持排空；已绑定节点的控制租约过期时，查询有效状态为 `offline`。首次绑定、进程重启或失联后恢复通信都会要求重新验收能力，不自动恢复 `ready`。正常持续心跳保留既有能力验收结论，但本身不能新增这个结论。

开户与重试使用同一个 `reserve_computer_node` 函数，取得行锁后才检查有效状态和剩余容量。即使锁等待前租约尚有效，也不能在锁等待结束后用过期租约预留容量；被拒请求不会留下新账户或开户操作。已在途开户仍由实际电脑检查、清理与对账确认结果，不凭控制心跳完成激活。

心跳失败不终止 API 的登录或历史查询；到期后的新增电脑被拒绝。systemd 的 API 单元使用 `Wants` 加 `After` 拉起节点及其安装前置流程，节点维护停止或启动失败不连带关闭已有用户的查询服务。门禁由租约与实际能力检查执行，不能用 API `/health/ready` 或系统服务启动通知替代。依赖语义依据 [systemd 单元文档](https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.unit.xml)。

控制租约本身不检查 Docker 或重建所有电脑执行状态；新增独立验收工作者负责固定镜像的实际能力检查与清理后发布，实际任务仍受节点会话与容器代理逐次授权。共享 Chrome 联合能力未通过前不能开户成功，公开远程电脑交互继续暂缓。

## 部署、回滚与验证

控制租约由 `0045` 引入，当前还必须执行 `0046` 的镜像能力门禁。先停止接单，再成套发布 API、节点程序和验收镜像配置；历史迁移不变。DDL 与触发器会取得节点目录结构锁，更新仅扫描节点目录，发布前评估目录规模与在途事务；不扫描用户业务表。升级会撤销无控制租约的旧就绪声明，保留容量及全部用户数据，不能靠手改 `ready` 跳过重新验收。

回滚保留数据库字段、控制代次、节点 `node-runtime.json`、用户卷和会话屏障，只能回到理解相同租约契约的成套版本。旧 API 会忽略过期控制状态，因此不能直接降级恢复接单；删除记录、回退代次或重建同 ID 不是回滚手段。节点状态恢复也须与目录中最高已确认代次一致，不能将旧备份当作新执行权。

常规测试使用真实临时 PostgreSQL，覆盖首次不授予就绪、并发乱序、重复回包、进程重启、旧进程回包、排空保留、过期恢复、行锁等待、数据库约束、开户及失败重试门禁、取消和迁移。节点记录测试覆盖并发序号、跨启动代次、损坏/权限/链接和溢出；`nodeintegration` 测试通过真实 TLS 双向证书端点与正式进程验证心跳，未登记证书在握手期被拒绝。以上不替代首次 Ubuntu systemd 安装、实际 Docker/磁盘/cgroup 和完整用户开户验收。
