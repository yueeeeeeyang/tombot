# TomBot 升级流程评审与重设计

设计提案，依据 2026-11-19 的代码和现场升级记录。本文的目标是让一次日常发布只影响实际变化的组件，让已经故障的节点仍有一条可验证的修复路径。提案中的阶段、命令和验收条件供实现使用。

## 当前一次升级经过什么

| 环节 | 今天实际执行的动作 | 成功证明了什么 |
| --- | --- | --- |
| 构建 | Linux amd64 构建脚本固定源码快照、编译管理前端和二进制。默认产出内嵌管理页面的 `tomd`、含五个程序的节点包。指定 `--with-image` 才额外构建镜像包。 | 包内容和架构通过构建检查。旧节点能否完成升级还需运行验证。[构建入口](../scripts/build_linux_amd64.py) |
| 服务端 | `tomd upgrade` 核对安装身份、配置、数据库连接和原文件，停止服务，使用 `pg_dump` 备份，核对快照后替换程序和服务单元。新进程启动时校验历史迁移并执行新迁移，通过健康检查后更新安装记录。 | 候选服务能够在当前数据库上提供 API。节点和用户电脑有各自的验收。[服务端升级](../internal/deployment/server_upgrade.go) · [数据库迁移](../internal/store/postgres/migrate.go) |
| 节点收包 | 本地入口从候选程序所在目录识别程序清单及镜像清单。远程入口由管理员上传、指定节点，节点的 systemd 定时器轮询已绑定的服务端，下载并验证归档。程序更新执行包内的 `tomnode upgrade`，单独的镜像更新执行已安装的 `tomnode upgrade --image-package`。 | 目标节点拿到了指定发布物。分片核验、上传续传、架构核验、已完成作业回执重发均可沿用。[远程更新器](../internal/deployment/node_update_agent.go) · [发布回执](../internal/deployment/update_receipt.go) |
| 节点安装 | 安装器取得本机锁，核对安装快照和原配置，准备按摘要存放的程序，然后先向控制服务查询旧电脑升级计划。遇到可恢复的隔离计划会先按已登记镜像恢复，遇到等待状态会轮询。安装阶段另行备份、申请维护、替换文件、启动服务并交还维护权。仅 Bot 程序变化且符合现有条件时，可原子切换入口。 | 常规路径返回 `control_started`。经历电脑恢复的路径还会等待验收并可能返回 `computer_ready`。[恢复编排](../internal/deployment/computer_recovery_upgrade.go) · [节点安装](../internal/deployment/node_repair.go) |
| 节点重新准入 | 维护会使旧的能力验收失效。心跳恢复后，验收器使用临时电脑执行检查和清理，成功后发布有期限的镜像验收结果。进入隔离的临时资源保留原身份。 | 节点满足接纳相应电脑的条件。已有用户电脑可能仍在另一代容器上。[节点验收](../internal/nodecatalog/verification_store.go) |
| 用户电脑切换 | `computerupgrade` 根据节点状态、心跳、镜像验收、维护窗口和租约领取计划。依次排空会话、停旧容器、在原用户盘上建立新一代容器、核对就绪回执，再以事务更新电脑和计划。聊天打开会话时检查这台电脑的状态。 | 目标用户的电脑已在指定代次就绪。此后打开新会话才能验证聊天链路。[领取条件](../internal/computerupgrade/claim.go) · [提交切换](../internal/computerupgrade/advance.go) · [聊天会话准入](../internal/computercontrol/acquire.go) |

桌面客户端另有按操作系统和架构发布、校验和安装的流程。整套发布只在 API 契约有依赖时才应要求先升级服务端，普通客户端发版可以独立进行。[客户端发布流程](client-updates.md)

## 为什么小改动也会卡住

1. **依赖判定发生得太晚。** 节点进入旧电脑恢复循环后，才有机会走到只更新 `bot-agent` 的分支。配置了本地离线镜像的节点在安装快照核对时还可能完整读取大归档并计算 SHA-256。小包已经减少了上传量，安装成本和阻塞范围仍与电脑镜像相连。[升级入口](../internal/deployment/node_repair.go) · [安装核验](../internal/deployment/install.go) · [归档核验](../internal/deployment/archive.go)
2. **修复程序有时排在它要修复的故障后面。** 本次维护窗口已关闭，心跳有效，电脑计划为 `draining`、尝试数为零、租约为空。临时验收电脑在更早的时候因 `agent_retirement_entry_unknown` 隔离，节点留在 `bootstrapping`。镜像工作进程因此领不到计划，恢复查询却持续返回 `waiting`。已有日志中的 `container_stop_unconfirmed` 是上一轮失败，当前阻塞原因是节点验收隔离。[恢复查询](../internal/nodeenrollment/recovery.go) · [节点维护规则](../internal/nodeenrollment/maintenance.go)
3. **同一资源格式由不同代码分别认识。** 拆包后节点写入了 `program-core`，上一代控制目录的清理规则漏掉了该文件。旧配置、旧容器标签和新旧发布清单也都位于版本边界。工作区的修复已覆盖 `program-core`，今后每种新持久记录都需要创建、读取、恢复、退役四个动作的测试。[程序选择记录](../internal/dockernode/programs.go) · [控制目录退役](../internal/dockernode/agent_retirement.go)
4. **不同界面回答了不同的问题。** 远程更新器上报 `started / busy / failed`，平台结合已登记镜像和节点验收推算作业就绪。程序包更新时镜像摘要可以完全相同，这种视图缺少独立的运行中程序版本证据。另一处节点详情曾因可选浏览器探针字段缺失而不能渲染。需要区分节点在线、节点能接新电脑、指定电脑能开会话和这次发布完成四项事实。[远程作业视图](../internal/nodefleet/admin.go) · [节点详情](../../admin/src/users/NodeDetailPage.tsx)

构建阶段也有可修的诊断缺口。源码白名单检查目前会报“构建源码出现未声明的文件类型”，错误消息没有给出相对路径。保留白名单，将构建输入固定到干净快照，并在失败时输出被拒绝的相对路径和适用规则。这样能在发布机上区分新增的合法构建输入与临时文件。[源码快照](../scripts/release_bundle.py)

## 按变更范围生成升级计划

继续交付 `tomd`、节点程序包、可选电脑镜像和独立的桌面客户端。节点程序包继续包含 `tomnode`、`computer-agent`、`computer-task`、`computer-probe`、`bot-agent`。复用现有 systemd 更新任务、本机安装锁、PostgreSQL 作业和按摘要存放的文件。第一版在现有模块内实现一个共同的计划入口，本地和远程调用它。

发布清单描述平台、各组件摘要、控制协议、配置及控制目录格式、镜像所需的挂载约定和支持的起始状态。计划器比较**本机实际运行和已安装的版本**与目标清单，冻结受影响的节点、电脑及验收项。范围可以合并。例如同时修改 `tomnode` 和 `computer-agent` 时执行两行相应动作。所有摘要相同且有匹配的运行回执时，直接返回已应用。操作员可以先查看计划，看到上传量、预计停哪些服务、影响哪些电脑和可用回退点。

| 实际变化 | 执行动作 | 发布成功的证据 |
| --- | --- | --- |
| 仅 `bot-agent` | 校验小包及当前节点支持的代理协议，原子切换 Bot 入口。已启动的会话用原进程结束，下次启动用新程序。 | 从实际入口启动一次隔离的协议自检，取得新 Bot 的版本和最小请求回执。该自检使用临时状态，独立于业务电脑和旧镜像迁移。用户电脑自身的可用状态单独显示。 |
| 仅 `tomnode` | 预置新宿主程序，持维护权短暂重启节点控制服务，保留电脑容器、代次和用户盘。计划列出需要先排空的任务。 | 新进程在受认证的节点通道上报告目标构建摘要、新实例身份和受支持协议，完成控制请求。 |
| 三个电脑基础程序中的任一个 | 预置三者的配套版本。按电脑排空，逐台让原容器装载新版程序。将这一动作从宿主启动恢复中提取为可单独领取的作业。 | 每台目标电脑报告新程序摘要，能打开并关闭会话，磁盘和桌面身份一致。 |
| 电脑镜像 | 仅传缺失镜像，按固定摘要预置并先用临时电脑验收，成功后逐台切换用户电脑。 | 目标镜像、容器代次、原卷、桌面和会话回执均匹配。所有目标都有终态，才能汇总整批结果。 |
| `tomd`、管理页面或数据库 | 管理页面随 `tomd` 发布。先核对节点协议范围及数据库迁移链，备份后执行服务端升级。 | 运行版本、数据库版本、API 和关键工作进程通过检查。 |
| 桌面客户端 | 沿用按平台发布和客户端签名或完整性检查。涉及 API 契约时在发布计划中写明依赖顺序。 | 候选客户端重新启动、连接服务并完成收发。 |

程序更新只读取它实际依赖的镜像身份和挂载契约。镜像进入缓存、导入、替换或完整性存疑时必须重验归档。例行的归档完整性巡检可以独立运行。节点身份、来源授权、程序摘要和用户盘归属始终是硬条件。

控制库沿用节点发布作业与逐台电脑迁移记录，用一个发布操作 ID 关联。发布作业保存目标、范围、阻塞原因和最终结果，电脑记录保存每台的源代次、目标代次、租约及结果。本机事务记录保存已落盘的步骤和上一版本。对同节点、同目标、同范围的活动请求返回已有操作 ID。冲突目标排队，只有当前写入者持有效控制版本才能推进，进程重启后先对账。CLI 和平台读取同一操作视图。控制端自身停机升级时由本机日志继续负责恢复。

## 一次发布如何推进

1. **预检和暂存。** 包直接解到本次发布专属的私有暂存目录，按清单认包。先核对空间、权限、平台、协议、配置迁移、回退版本及用户盘身份，完成所有可提前执行的下载和校验。控制服务或节点离线时可以暂存，在线授权恢复后才执行需要维护权的动作。
2. **取得范围明确的维护权。** 控制端先关闭目标范围的新任务准入，再等待现有任务结束。到期仍有运行任务时返回任务数、截止时间及阻塞原因。已开始的非幂等动作保留其回执核对流程。仅更新 Bot 入口时无需取得整节点维护窗口。
3. **激活和记录。** 更新器作为现有 systemd 独立任务运行，其启动入口保留一个已验证、可用来启动或回退宿主程序的版本。候选程序写入独立版本目录，文件刷盘后原子切换指针。切换前记录原版本、目标版本和操作 ID。崩溃后同时读取指针、运行进程和本地记录决定下一步。更新器自身的更新最后单独确认。
4. **按范围验收。** 节点控制能力、运行环境能力、用户电脑可用性分别记录。镜像发布先在独立测试盘上完成连续两代“创建、打开桌面、关闭、退役、再次创建”，然后才迁移真实电脑。真实电脑使用原卷，只有确认旧实例退出且原卷没有另一个写入者，才允许新版挂载。Chrome 按桌面按需启动，浏览器能力由需要它的验收项单独检查。
5. **提交并放行。** 控制端凭操作 ID、目标摘要、实例身份和代次提交对应结果，逐个释放已经通过的范围。对同一回执重复确认，对旧租约和乱序回执拒绝推进。发布历史固定保存当次结果，节点当前健康可以继续变化。运维能同时看到“宿主程序已生效，电脑迁移 8/10，1 台重试，1 台隔离”。

### 已隔离的节点怎样装上修复版

这是设计能否解决本次故障的关键验收场景。对“宿主程序变化、镜像和存储契约不变”的计划，控制端应能授予**只允许更换宿主程序的维护权限**。在同一事务中暂停新的电脑切换领取，核对活跃会话、节点验收租约和已发出的节点动作。节点再核对本机锁和落盘操作。只有确认旧动作已结束，或已按控制版本交接，才可激活修复版。身份不符、卷归属不清或仍有未知写入时，只允许暂存并明确报告阻塞。

新版 `tomnode` 启动并完成控制握手后，可在原操作身份下重新核对**原隔离的临时电脑**。针对已知且经过本机验证的故障，每个修复版本最多自动重新核对一次。成功后恢复原镜像计划并继续验证用户电脑。遇到未知文件、活跃挂载或代次冲突时保留隔离，并把具体错误返回到 CLI 和平台。节点控制程序可修复、业务接单继续受限，这两个结果可以同时成立。

## 失败、回滚和用户反馈

| 中断点 | 恢复规则 |
| --- | --- |
| 上传中断、空间不足或清单不合 | 暂存结果按摘要复用或丢弃。预检失败时原版本继续运行。 |
| 切换前后断电、节点离线、回执丢失 | 本地记录回答“实际动了什么”，控制库回答“授权做什么”。用同一操作 ID 和目标摘要重放，先读取事实，再决定续跑、补发回执或回退。数据库事务内只更新授权和事实，Docker 与 systemd 调用放在事务外。 |
| 新宿主程序起不来 | 由可独立启动的本机更新器在有界期限内回到已验证的上一程序及匹配配置，重启并核对实际版本。回退也失败时保留备份与现场，停止扩大批次。 |
| 电脑切换失败 | 预检或试运行失败时，原电脑继续服务。真实切换已开始时，核对原卷和唯一写入者。只有旧程序能读取当前盘数据且有明确退出证据，才允许在原盘回退。涉及不可逆数据格式变更，先做可恢复快照，后续以前向修复或经确认的一致恢复为准。 |
| 服务端 SQL 已提交，新 API 启动失败 | 新增前向迁移且逐版校验。当前旧 `tomd` 会拒绝陌生的迁移版本。回滚前必须用待恢复二进制验证数据库、配置和协议兼容性。跨越不可逆边界时采用前向修复或成套恢复，并处理备份之后的新写入。 |

CLI、平台列表、详情和升级页共享同一组诊断数据。每个操作至少提供作用对象、当前阶段、目标与实际版本、最近进展、当前阻塞原因、下一次动作或截止时间、允许的恢复操作。过去的错误保存在历史里。本次现场应该直接显示“节点在线，临时电脑验收已隔离，用户电脑切换尚未领取”，并展示 `agent_retirement_entry_unknown`。命令行关闭后，已受理的后台作业仍能按 ID 查询和续接。聊天对受影响的电脑提示维护或恢复状态，已接收的请求保留原运行编号。

为下载、排空、启动和业务验收分别设置阶段超时、退避间隔和最大尝试次数。区分“有进展但耗时长”“前置条件已经失败”和“上次动作结果未知”。首类更新进度，第二类立即报告阻塞，第三类先核对本地和服务端回执。CLI 等待超时只结束本次等待，操作结果仍以持久记录为准。

## 改造顺序和上线门槛

| 批次 | 修改入口及交付 | 放行条件 |
| --- | --- | --- |
| 1. 消除错误等待 | 在 `nodeenrollment` 和 `nodefleet` 汇总节点验收、维护和电脑计划。CLI 和管理平台消费同一阻塞原因。迁移前先检查旧接口能接受的字段或协商能力。 | 复现本次现场，第一次查询即可区分“正在执行”和“已经隔离，无法领取”。节点详情缺少可选探针时仍可打开。 |
| 2. 拆开宿主和业务安装 | 在 `deployment` 先按摘要生成计划，将纯 Bot 更新和受限的宿主修复移到电脑恢复循环之外。本地与远程使用同一执行器，持久化阶段和实际版本。 | 单台节点、容量已满、旧电脑已隔离时，仍能安全安装修复宿主。重复提交、服务重启和回执丢失均不会再次停机。 |
| 3. 逐台迁移电脑 | 在 `computerupgrade` 和 `dockernode` 复用现有代次、租约及原卷核验。区分节点的候选镜像与已通过验收的镜像，逐台设置切换目标。会话准入按该电脑的实际目标判断。 | 同节点两台电脑中一台升级失败时，另一台仍可接单。两个 Bot 同时操作各自桌面不串屏，关闭一个 Chrome 后另一任务继续。切换前后工作区文件和按桌面保存的登录态均在。 |
| 4. 分批发布与回滚演练 | 控制端先选代表性节点，观察接单成功率、不可用时长和回滚结果，再放开下一批。单节点环境用独立测试盘和预留资源做预检，实际重启安排维护窗口。 | 完整发布物在真实 Linux、systemd、Docker 和 PostgreSQL 环境完成升级与恢复演练。试点触发故障即暂停后续批次。[Google SRE 的小范围发布实践](https://sre.google/workbook/canarying-releases/) |

迁移现有节点时，先更新能识别新作业的控制端，通过一次受控引导登记各节点实际安装版本。已有在途计划按原 ID 收尾，或在确认租约与资源身份后由新执行器接管。旧共享浏览器配置通过一次显式迁移生成新配置，保留原始快照和身份。数据库变更只追加新的迁移，先增加可选字段和必要索引，在试点完成后再启用新执行路径。暂停推广时让已领取作业到达可确认边界，再恢复原执行器或使用前向修复。

每次发布至少从上一正式版本和仍在使用的最老布局升级，另测首次安装、重复执行、磁盘满、网络中断、宿主重启、丢失停止回执、旧回执晚到、备份恢复和新进程启动失败。验收记录包含真实包摘要、每台电脑的代次、原卷、应用结果与会话结果。单独安装新版本成功只能覆盖首次安装这一项。
