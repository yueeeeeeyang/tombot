# 客户端升级

管理平台的「客户端升级」展示各平台已发布的最高版本。点击「发布版本」，选择与安装包匹配的系统和架构，填写实际客户端版本号及用户可见的升级内容，再上传文件。版本号采用稳定版的三段整数格式，如 `1.10.0`，每段最多六位。单包上限 1 GiB，升级内容最多 4000 字。

| 系统 | 架构 | 「立即升级」应上传的包 | 可单独下载的其他包 |
| --- | --- | --- | --- |
| macOS | arm64、x64 | 包含同一签名 TomBot.app 的 ZIP | DMG、PKG |
| Windows | arm64、x64 | 同一发布者签名的每用户 NSIS EXE | MSI、ZIP |
| Linux | arm64、x64 | TomBot AppImage | DEB、RPM、tar.gz、ZIP |

分片上传与最终发布均使用管理会话、CSRF 和敏感操作再验证。每次上传一个 4 MiB 分片，服务端核对 SHA-256 后写入私有目录。所有分片就绪后，发布记录与管理审计在同一事务中提交。同平台同版本只能发布一次，分片失败后可以重新选择原包上传。多个平台独立生效，版本按数字大小排序。

## 客户端接口

- `GET /api/v2/client-updates/latest?platform=darwin-arm64&version=1.9.0` 返回本平台严格高于已安装版本的最高发布记录。没有匹配版本时返回 `{"release":null}`。平台前缀为 `darwin`、`win32`、`linux`，后缀为 `arm64` 或 `x64`。
- `GET /api/v2/client-updates/{id}/parts/{index}` 返回已发布版本的指定分片。版本说明及安装包对能够访问服务地址的客户端公开。下载请求沿用主进程保存的证书信任，无需携带用户会话。
- 管理端使用 `GET /api/v2/admin/client-updates` 读取平台和当前版本，使用 `PUT /api/v2/admin/client-updates/parts/{sha256}` 上传分片，最后通过 `POST /api/v2/admin/client-updates` 提交版本、平台、说明、后缀、大小及有序分片摘要。

## 部署与回滚

1. 备份当前数据库、服务配置和单元文件，使用包含本次管理页面的服务端发布包执行 `tomd upgrade`。新增迁移 `0081_client_releases.sql` 只创建发布表和索引，耗时主要是空表建表与授权，迁移期间不扫描或改写既有业务表。
2. 升级命令会安装随包的 `tomd.service`，systemd 为 API 账号创建私有持久目录 `/var/lib/tombot-client-releases`。自定义部署可在服务配置的 `client_release_directory` 指定规范绝对路径，预先赋予 API 账号读写权限。多实例须共享支持原子重命名的同一发布目录并连接同一数据库。
3. 安装首次支持检查更新的桌面版本。后续在管理平台按平台发布，安装包内的应用版本号应与页面填写值一致。用户点击「立即升级」后自动下载、校验、安装并重启。正式客户端的打包配置见[桌面发行说明](../../desktop/README.md#桌面发行与自动安装)。
4. 数据库保存清单，文件目录按摘要去重。容量和备份应覆盖保留的安装包及中断上传留下的分片。备份时先记录数据库快照，再备份对应文件。恢复时同时恢复数据库和该快照引用的所有分片。
5. 已发布的安装包不可原地替换。修复有问题的客户端发行版时，使用更高的版本号重新构建和发布。回滚单台桌面客户端可重装原安装包。整体回退到旧服务端时，应在维护窗口使用匹配旧构建的数据库备份、配置与单元，先保全并核对备份之后产生的业务数据；旧服务端会拒绝未知迁移版本。
