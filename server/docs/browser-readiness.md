# 桌面 Chrome 与电脑就绪

每个聊天桌面和后台任务桌面都有稳定的桌面 ID。打开 Chrome 使用该桌面的 Xtigervnc 显示、X11 认证和独立进程。观看连接复用现有 RFB、WebSocket 和 noVNC 通道。打开观看窗口、执行终端命令和检查整机状态均无需启动 Chrome。

## 打开与诊断

模型用 `computer_browser` 的 `{"action":"open"}` 打开或聚焦窗口，再用 `computer_screenshot` 和 `computer_input` 导航、填写表单和操作文件选择器。用户可在 XFCE 菜单中打开 Chrome。启动回执要求本桌面的实际 Chrome 进程存在可见窗口。失败时先查看当前桌面，再决定是否重新打开。正常结束桌面时，在现有租约内给 Chrome 最多三秒提交站点数据，然后回收执行组和临时认证。崩溃或强制撤销时，恢复以 Chrome 已写入磁盘的数据为准。

电脑就绪仍要求终端、文件、进程回收、磁盘配额及网络隔离的探针全部通过。浏览器的显示、启动或窗口问题只对该桌面的打开操作报告失败。关闭 Chrome 后仍可运行 Shell、观看原桌面并使用其他桌面。并发打开几个桌面会运行几个 Chrome 实例，均计入同一台电脑的内存与进程限额。

## 持久盘和升级

同一块用户配额盘上的 `workspace` 保存共享文件，`desktops/<desktop_id>` 保存该桌面的浏览器配置、Cookie 和本地站点数据。节点将 `desktops` 挂至 `/var/lib/tombot-browser`。根目录归 root 所有且权限为 0711，每个配置目录归专属浏览器 UID 所有且权限为 0700。下载进入共享的 `/workspace/Downloads`。同一个桌面在新的执行会话中复用登录状态。聊天桌面和独立任务桌面分别首次登录。

升级前暂停接单、排空活动桌面和观看连接、保存用户盘与节点控制记录。升级节点与服务端，按新版 `deploy/node.example.json` 移除节点配置的 `browser.limits`，保留历史服务回收的三项超时。使用同时标记 `io.tombot.computer.storage-layout=2` 和 `io.tombot.computer.desktop-browser=1` 的新镜像，通过保盘换镜像流程替换旧容器。节点复核并排空旧共享服务，旧 `browser` 配置目录保留在磁盘上。新容器只挂载独立桌面配置根，已有用户需要在各桌面重新登录。本次浏览器变更无需 SQL 迁移。

回滚时先停单、排空，并另存升级后产生的工作文件和桌面配置。恢复配套的旧节点配置、控制记录、电脑镜像与升级前磁盘快照，再恢复接单。旧节点会拒绝带新增顶层目录的磁盘。不要将多个登录配置合并写入旧共享目录。

## 验收

在 `server` 目录构建镜像后执行 `make test-computer-image`。验收使用无外网的临时卷和本地测试站点，实际运行两个 XFCE、Xtigervnc 和 Chrome，通过各自的 RFB 连接并发输入，检查一个浏览器正常退出及崩溃时另一桌面、原桌面终端与观看连接的状态。随后用同一卷重建容器，换执行会话，验证两个桌面的站点 Cookie。
