# 浏览器能力验收与升级

节点通过受保护的代理通道发送当前浏览器授权和新随机挑战。代理只检查该活动授权，不缓存或重放旧能力回执。实际检查包括 Chrome 的 PID、网络命名空间和 Seccomp-BPF 沙箱、经过节点出网代理加载页面、截图尺寸与像素、鼠标定位及文本输入、两个独立窗口的 cookie/localStorage 共享，以及测试数据和全部临时窗口的确认清理。

诊断页使用保留域名 `tombot-probe.invalid`，只由通过内核对端身份检查的节点代理提供，不依赖第三方网站。它证明浏览器到代理的真实链路，不代表所有外部网站均可访问。探针不进入业务窗口目录，不读取用户页面或已有登录信息。检查和清理均有期限；清理未知则封闭共享浏览器，不返回成功。跨进程只传固定错误分类，日志包含电脑、用户、挑战和失败阶段。

节点再复验当前容器、资源组、授权以及基础终端、文件、磁盘配额、进程回收和网络隔离证据。只有全能力通过且验收电脑已确认清理，服务端才发布有时限的节点就绪资格，允许创建用户电脑。

## 已安装节点

探针包含容器内代理代码，旧节点必须更新完整电脑镜像，不能仅替换宿主二进制。先升级配套 `tomd`，再把新的同架构离线包完整解压到受保护目录并执行：

```bash
sudo ./tomnode upgrade
```

安装器保留节点标识、证书和接入凭据，核验新归档后使用可恢复文件计划切换程序与配置。服务端只接受原证书签名且匹配上一镜像身份的升级。预留电脑可以随节点保留，未到期的验收租约仍会阻止切换。节点服务重启期间当前会话可能中断，管理平台在新镜像验收后恢复新电脑分配。

新镜像有独立登记身份。服务端撤销旧能力证据并切换监督器，按原操作身份清理隔离验收资源，再创建下一代验收电脑。新版 `tomd` 在节点通过新镜像验收后排空该节点已有电脑的旧会话，保留其原磁盘并换用下一代容器。验收电脑和既有电脑分别核对能力，只有目标容器验收成功才将该电脑交给 Agent。具体维护及完成日志见[节点运维](../deploy/NODE.md#管理平台远程升级)。

## 数据迁移、恢复与回滚

允许有预留电脑的节点升级只需部署配套 `tomd`，沿用现有镜像登记和节点维护表。更新节点行、连接镜像、旧验收记录和审计在同一事务执行。节点行锁协调新分配，未到期的验收租约阻止与在途验收竞争。旧监督器在事务中核对当前镜像，镜像切换后由新监督器接管。

文件升级失败后保留原身份和 `/etc/tombot/node-repair` 计划，使用相同程序、安装包目录和参数重试。成功后计划归档至 `/etc/tombot/node-repair-*`；旧镜像归档保留。不得手工清空验收账本或把状态改成就绪。

使用上一份支持此升级协议的完整离线包执行同一命令，会登记另一独立镜像并重新验收。服务端尚未接受首次切换时，可以从备份恢复整套程序、配置与安装记录。若回退服务端的预留门禁改动，先完成在途维护，再恢复与当前数据库版本匹配的 `tomd`，旧版会重新检查预留数。

## 验证范围

ARM64 Linux 的真实 Chrome 已通过全项检查，连续两轮检查保留了业务窗口，断开真实 Unix 出网代理后下一轮明确失败。原生浏览器检查使用生产 seccomp、非 root 浏览器、只读容器根目录和无外网网络模式。

本机 Apple Silicon 的 x64 模拟运行中，Chrome 报告 Seccomp-BPF 未启用，探针因此正确拒绝就绪；没有关闭或弱化该检查。生产 x64 的完整宿主 cgroup、磁盘挂载及用户电脑供给仍需在原生 Linux x64 节点验收，不能把本地分层测试视为远端服务器已经就绪。

## 浏览器启动失败诊断

原生浏览器冷启动预算从节点 `api.call_timeout_ms` 中分配，为代理准备、基础探针和浏览器探针留出时间，最低为普通浏览器控制调用预算。新版默认节点调用上限为 60 秒，为 Xpra 与 Chrome 冷启动预留 35 秒。节点签发一次绝对期限，代理用它覆盖全部 CDP 初始化，活跃浏览器的普通操作仍使用原有 5 秒预算。代理将可确认的 CDP 启动超时记录为 `browser_start_timeout`。启动失败后，确认进程退出、资源组清空和控制入口释放后才写入关闭记录，启动失败分类仍会保留。无法确认回收时，代理继续执行原有退出隔离流程。

升级需要配套的 `tomd`、`tomnode` 和含新版电脑代理的离线镜像。已有集群先保留 `tomd` 的现有节点调用预算，逐台升级节点。等所有受此服务调度的节点支持 60 秒调用后，将服务端 `node.call_timeout`、`node.control_lifetime`、`node.verification.lease_duration` 分别设为 `60s`、`4m`、`5m`，同时将 `provision.call_timeout` 和 `provision.lease_duration` 分别设为 `60s` 和 `3m`。重启 `tomd` 后，在管理平台重新核对故障节点验收。本次无需迁移数据库或用户磁盘。回滚时先恢复服务端原预算，再使用上一份完整节点包回退。节点升级的备份与恢复步骤见[节点运维](../deploy/NODE.md#重试升级与回滚)。

宿主与容器可以处于不同时间命名空间。曾有部署的电脑身份和启动预算正确，但节点签发的期限绑定宿主命名空间，代理因此在启动 Chrome 前拒绝请求。节点现在从已核验的容器主进程读取内核时钟偏移，换算原绝对截止时间并绑定接收方命名空间；浏览器、基础探针、会话开启和续约一起修复。代理的过期、最大租期和命名空间校验保持严格，传输耗时不会重新获得租期。

此次时钟修复不修改数据库或授权记录格式，使用完整离线节点包按上面的 `upgrade` 流程升级即可，已支持升级维护协议的 `tomd` 无需更换。换算前后复验容器 PID、配置与资源组身份，无法确认或发生变化即拒绝签发。回滚仍须排空并整体恢复上一份节点包；不同命名空间环境会恢复原拒绝行为，不能回滚后手工标记就绪。

`browser_start_unconfirmed` 表示节点没有收到可信的浏览器启动成功回执，不能直接归因于 AppArmor 或某一项能力。新版将引导身份、启动授权、目录权限、私有管道、cgroup 入组、降权、程序执行和 CDP 初始化分别分类；已知 Chrome 沙箱或 profile 错误同样显示固定分类。

启动前的共享时钟、电脑身份、入口数量、部署预算和已消费授权也返回固定分类；这类拒绝不会创建浏览器或写入启动意图。`browser_start_deadline_failed` 表示共享单调时钟读取、时间命名空间或原期限校验失败，不能通过重置期限绕过；`browser_start_budget_failed` 表示授权预算超过代理限制；`browser_start_state_failed` 表示原授权已消费或代理已封闭接单。它们经原控制通道返回，避免被统一折叠成 `browser_rejected`。协议不增加字段，沙箱与执行权规则不变。

启动诊断仅在内存中暂存最多 64 KiB 前缀，启动结束即清空；后续输出继续丢弃。原始网页地址、页面内容和 stderr 不入日志、不返回管理平台。快速退出时有界等待进程和输出排空，不把管道先关闭导致的诊断缺失当作成功。失败仍回收原授权和受管资源组，不重放启动，也不修改沙箱、权限或就绪规则。

浏览器启动失败后的清理也可能失败，独立看门狗随即退出整个代理，导致具体错误回执丢失。代理现在先撤销该实例的执行权，再将固定启动分类原子写入私有 `browser.json` 的 `startup_error` 字段，然后继续原有清理与致命退出流程。记录携带完整授权，只允许已消费或已关闭状态；保存诊断失败仍使代理退出。关闭屏障保留同一授权的诊断，新授权不会继承旧错误。

节点收不到启动回执时，只读取本代容器受保护目录中完全匹配当前授权的诊断。未知分类、其他授权、活动状态附带失败、权限漂移和符号链接均拒绝；读取诊断不会发放能力、重试启动或跳过原实例回收。这使代理退出后仍可定位失败阶段，不依赖容器日志保留时间。

此项不修改数据库；私有代理记录新增固定分类字段，需成套更新宿主 `tomnode` 和离线镜像，使用上面的 `upgrade` 流程。现有 `tomd` 可显示错误码，更新页面后显示中文分类。回退不认识新字段的旧包前，必须由新版确认旧验收容器和代理控制目录已回收；不能手工删除记录或仅回退二进制。新增诊断帮助确认实际失败阶段，不代表远端节点已经通过验收。
