# 工作台本地通知

登录后，客户端在打开工作台、切回前台、重新连接或收到审批与回合状态变化时，读取服务器上的最新状态。有可处理的审批时，工作台显示“查看待办”。已打开的待办页回到前台也会刷新。审批是否仍可提交，由服务器在提交时再次核对。

同步错误、连接降级、布局保存错误与待办提示以圆角卡片显示在聊天输入框正上方，与输入框左右对齐，不再跨越侧栏和聊天区。重新同步与布局重试沿用原操作，提示更新不清空输入草稿。多个提示占用较多高度时独立滚动，保留输入和发送空间。没有打开会话时，提示显示在主内容区底部；待办和设置模态打开后，底层提示不穿透遮罩。

在“我的／已授权设备”中启用“本机系统通知”。此选项按当前设备和服务器分别保存，初次使用时默认关闭。iOS、Android 和 macOS 按系统要求请求授权。拒绝授权或发送失败时可继续在工作台处理审批，设备页显示系统通知的错误。移动端前台恢复后同步，应用被系统挂起期间不依赖远程推送。

通知中心只显示标题 `Tom` 和“有待审批事项，请打开查看”或“任务已完成”。点击分别进入待办或对应会话。点击载荷只接受当前服务器的固定路由。审批决定、工具参数、域名、工作路径和消息正文均不写入系统通知。

## 同步与去重

已授权的 `GET /api/v1/notifications/status` 返回 `pending_approval_id` 和 `completed_turn`。没有对应记录时字段值为 `null`。完成回合只返回 `id`、`conversation_id` 和毫秒时间戳 `finished_at`。用户或例程发起且已成功的回合参与提醒；服务内部的协作回合与失败回合不触发完成提醒。

通知快照与点击路由共用会话标识校验：接受普通 ULID 会话和默认 Tom 的固定会话 `tom-direct`，拒绝额外路径、查询参数或其他非 ULID 标识。审批和回合标识仍须为 ULID。

每次只取最新的可处理审批和成功任务。批量离线积压合并为一条待办提醒和一条完成提醒。首次读取以已有完成回合作为起点。每个实例分别记住已投递审批和任务的位置，同一毫秒结束的任务以回合 ID 排序。工作台全局事件 `notifications.changed` 的载荷为 `{}`；会话内的 `turn.finished` 仍提供原有活动字段。快速重放或切回期间的重复读取合并，在途快照返回后最多补读一次。提醒按类别使用固定的系统位置，客户端读写进度或投递失败时可重新同步。

快照的 `pending_count` 统计所有仍可处理的审批。会话列表及其增量事件还包含 `has_active_turn` 与 `unread_artifacts`。待办入口将这三项相加。产物按读取游标之后的非用户消息块统计，支持独立产物块和工具结果携带的文件。归档会话随工作台列表一同移除。读回合、审批与产物使用现有设备权限。

Linux 通过会话 D-Bus 和桌面的通知服务交付，进程运行时接收默认动作。Windows 桌面通知的撤回需要具有包身份的 MSIX。平台能力详见 [flutter_local_notifications 平台说明](https://pub.dev/packages/flutter_local_notifications)。

## 升级与回滚

默认 Tom 通知校验修复只需重新构建并更新客户端，无服务端接口、数据库结构或数据迁移。现有通知进度继续有效。回滚时恢复此前客户端即可，但默认 Tom 的通知误报会重新出现。

提示布局调整同样只更新客户端，不修改通知进度或布局偏好的存储格式；恢复此前客户端即可恢复旧提示位置。

先停机备份，再升级服务端和客户端。新增迁移 `0015_notification_snapshots.sql` 在事务内为成功回合和待审批记录创建部分索引。首次升级会扫描这两张表并在创建索引时占用写锁，耗时与历史规模和存储有关。此后每次读取使用索引按序取首条符合条件的记录。客户端应与提供快照接口的服务端一起升级。

需要回滚时，先停机保存升级后新增的数据，再按[备份与恢复](backup.md)还原升级前的数据目录与匹配的服务端、客户端。直接使用历史程序打开更高版本数据库会触发迁移保护。已显示的系统提醒可在系统通知中心清除。

迁移 `0016_workbench_inbox.sql` 在现有消息和回合表上建立两个部分索引，用于读取指定会话的产物候选消息及活动回合。索引创建在单次迁移事务中进行，历史越多，初次升级持有写锁的时间越长。部署时先停机备份，再一并升级服务端与客户端；回滚使用对应版本的完整备份。

## 验证

在仓库根目录运行 `go test -race ./internal/service ./internal/httpapi ./internal/store`，在客户端目录运行 `flutter test test/notifications_test.dart test/workbench_notices_test.dart`。这些测试覆盖鉴权、索引、过期审批、同毫秒排序、事件隔离、前台恢复、系统授权失败、跨实例点击和重放去重，并验证默认 Tom 的快照同步、通知投递与点击、非法会话标识拒绝以及错误恢复。提示布局另覆盖桌面与手机对齐、圆角、重试后保留草稿、空工作台入口及大字体与键盘同时出现时的可操作性。

在安装了 Xvfb、Dunst、D-Bus、GLib 和 Flutter 的 Linux 图形构建环境，下面的命令会启动独立的通知服务，检查真实系统动作、撤回和通知历史中的中文正文。

```sh
dbus-run-session -- xvfb-run -a sh -ec '
  dunst -config /dev/null &
  TOM_ISOLATED_NOTIFICATION_BUS=1 flutter test -d linux integration_test/linux_notifications_test.dart
'
```

在 macOS 或 Android 的图形会话中，可从客户端目录运行 `flutter test -d <设备号> --dart-define=TOM_TEST_NATIVE_NOTIFICATIONS=true integration_test/system_notifications_test.dart`。Mac 的设备号为 `macos`。允许通知后，从系统通知中心点击待审批提醒。用例会核对系统保存的正文、客户端收到的载荷、工作台实际打开的待办页，以及任务完成通知的撤回。macOS 原生应用和 Android 14 ARM64 模拟器均已通过此流程。

自动化桌面验收另行运行 `integration_test/macos_notification_settings_test.dart`。用例按系统当前授权状态分别检查投递与撤回，或检查拒绝投递时的明确错误。本机未授权和已授权的状态可以分别复验；启动测试不会改变系统偏好。
