# 用户与电脑同步开户

本模块使用 PostgreSQL 控制连接管理普通用户开户。创建用户、激活材料签发、失败重试和隔离资源对账都通过同一领域服务完成。管理员不属于本模块：管理员账号由 [administrators](../administrators/service.go) 独立管理，不持有电脑也不进入开户工作池。HTTP 位于 [adminapi](../adminapi/README.md)，实际电脑操作由受信节点实现 `computer.Runtime`。

当前已经验证数据库与协议流程；节点接口在测试中使用可注入故障的替身，尚未接入真实用户容器。不能把状态机测试通过视为容器验收完成。

`ListUsers`、`ListNodes`、`ListImages` 为管理界面提供分页目录，读取前复验当前管理员。用户、电脑和操作关联在同一查询内读取；节点仅返回状态和容量，不暴露连接地址。目录不返回认证材料或用户内容，也不授予跨用户业务访问权。节点和镜像选择仍需在开户事务中再次验证状态与容量。

## 成功与超时语义

`Create` 首先检查管理员及近期二次验证。在短事务内规范化用户名、预留节点容量，并创建 `provisioning` 用户、电脑和操作记录。操作请求摘要包含全部业务参数；相同幂等键、操作者和参数复用同一操作，参数不同则冲突。请求标识不影响业务幂等。

`Run` 使用独立于请求的服务生命周期上下文。工作者以 `FOR UPDATE SKIP LOCKED` 领取操作，持久保存租约、控制代次和下次对账时间，数据库事务不跨节点调用。客户端断开或等待超时后，工作者继续处理同一操作。

每次领取后先 `Inspect`，逐项核验操作、用户、电脑、实例代次、控制代次、持久卷和容器标识。节点必须验证终端、浏览器、文件、进程回收、磁盘配额和网络隔离能力；只有全部通过，才在一个事务中写入电脑 `ready`、用户 `pending_activation`、操作 `succeeded` 及审计。此时创建请求才可返回成功。

请求超时返回 `ErrPending` 和已有操作；HTTP 对应 `504`。不得把“已受理”展示成“已创建”。超时后查询原操作，或用原幂等键重发原请求；不能自动产生新幂等键。用户激活另行完成，创建成功不代表已经设置登录凭据。

## 故障与恢复

| 情况                       | 持久结果与下一步                                                                          |
| -------------------------- | ----------------------------------------------------------------------------------------- |
| 节点响应丢失               | 进入有界对账；先检查资源，不能直接重建                                                    |
| 电脑已就绪但最终事务失败   | 租约到期后重新领取，观测原电脑并提交同一操作                                              |
| 确认创建失败               | 进入补偿，节点确认本次未投入使用的容器、卷和网络全部不存在后才释放容量                    |
| 无法确认清理或资源身份不符 | 进入 `quarantined`，账户不可登录，保留用户名和容量                                        |
| 显式恢复隔离操作           | `Reconcile` 只重新核实和清理同一实例，不调用创建；确认清理完成后操作仍为 `failed`         |
| 重新开户                   | `Retry` 只接受已确认清理的失败操作，保留用户及电脑 ID，增加尝试号和实例代次，重新预留容量 |
| 旧工作者返回               | 数据库拒绝过期租约或旧控制代次；节点也必须持久拒绝旧控制者                                |

对账和清理都有截止时间、次数上限及退避。节点未知结果不能转换为成功或资源不存在。隔离恢复只接受从未就绪、未签发激活材料且仍处于开户失败状态的电脑，不能清理已经投入使用的用户电脑。

服务退出时取消节点调用并保留持久操作，由下次启动恢复。数据库和审计异常从工作池返回启动入口，不能静默继续运行一个已失效的开户工作池。

## 激活与首次部署

`IssueActivation` 仅接受电脑已经就绪的待激活账户，使用安全随机值，数据库只保存摘要；再次签发会在同一事务中废止旧值。查询用户或操作不返回激活值，日志和审计也不记录它。后续 `identity.Activate` 再次锁定用户并检查电脑状态。普通用户不使用动态验证；动态验证只属于管理员身份。

首位管理员不再经过本模块：管理员无需电脑，由受保护的本地部署命令 [`tomadmin-bootstrap`](../../docs/admin-bootstrap.md) 直接写入管理员账号与激活材料；追加管理员账号在管理平台完成。本模块不注册任何首位管理员专用方法，也不存在免电脑用户。

`Options` 必须由部署配置提供工作者数、节点调用时限、租约、操作及请求时限、重试上限、激活有效期和用户额度。`DesktopConcurrency` 必须显式设置为 1–64，与模型并发额度独立，开户时同事务保存为 `user_limits.concurrent_desktops`；同键重试保留原额度，不因部署设置变化覆盖已创建用户。租约至少覆盖三个节点调用时限；节点对租约实际到期和代次的校验仍不可省略。

## 数据变更与验证

新增不可变迁移 `0032_user_provisioning_operations.sql`，记录对账次数、下次尝试、容量预留和请求标识，并增加领取索引及电脑首次就绪时间。不修改 `0001` 至 `0031`，不读取或转换 SQLite 数据。

迁移包含短事务结构锁及索引创建；当前目标是新空库，未来已有大量操作记录时须评估锁等待、表大小及部署窗口。执行失败由事务回滚；应用已运行后的结构修正使用更高版本前向脚本，禁止删除迁移账本或降级数据库。

真实 PostgreSQL 竞态测试覆盖：同步等待、请求超时后继续执行、并发幂等、容量预留回滚、节点回包丢失、最终提交失败恢复、清理前不释放容量、隔离恢复、旧租约拒绝，以及开户、激活轮换、激活、登录的完整联动。首位管理员的创建与重新签发由 `administrators` 与部署测试覆盖。真实容器、节点故障和进程隔离验收仍需在节点运行器接入后执行。
