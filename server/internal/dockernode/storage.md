# 用户持久磁盘与硬容量

`FileStorage` 为每次初始用户电脑供给及节点专用验收分配独立、固定长度的 ext4 镜像。宿主先预分配容量，再建立 loop 设备和文件系统挂载；Docker 只绑定该电脑已核验的挂载目录。数据保存在持久镜像中，服务退出不卸载或删除用户磁盘。

当前已通过状态机、故障与安全边界测试，以及无需设备权限的真实 Linux 镜像验证。完整挂载、写满后的 `ENOSPC`、占用拒删和重挂载测试已经编写，但高权限执行尚未获授权，不能宣称硬容量运行验收完成。

## 容量与身份

ext4 根目录为 root:root、0755，不直接映射进容器。固定 `workspace` 子目录为 root:20000、2770，挂载到 `/workspace`，所有 Bot 共享业务文件和工具；固定 `browser` 子目录为 30000:20000、0700，挂载到 `/var/lib/tombot-browser`，供同一用户的共享 Chrome 服务持有账号状态。两个子目录使用同一个 Docker 卷及同一块配额磁盘，不按 Bot 划分文件空间。`lost+found` 留在磁盘根目录。

节点在启动容器前创建子目录，使用固定 `VolumeOptions.Subpath` 和 `NoCopy` 挂载并在对账时核对；缺失、交换子目录或扩大为整卷均失败。Docker 子目录挂载要求目录预先存在；固定 Engine API v1.47 包含该能力。[Docker 卷子目录说明](https://docs.docker.com/engine/storage/volumes/)、[Engine API 版本记录](https://docs.docker.com/reference/api/engine/version-history/)。镜像必须携带 `io.tombot.computer.storage-layout=2`，旧镜像在分配磁盘之前拒绝。

`FileStorageOptions` 指定 root 保护的数据目录、独立控制目录、单命令时限和宿主最低空闲余量。每个代次使用 `tombot-<computer_id>-g<generation>/filesystem.img` 和同级 `workspace/` 挂载点。控制记录按用户保存为 `<user_id>.storage.json`，采用版本 3；锁为 `<user_id>.storage.lock`，跨代次复用同一 inode，不删除或替换。控制目录位于用户存储之外，不向任务暴露底层镜像、loop 设备或宿主工具。

镜像先通过 `fallocate` 分配空间，再核对文件长度与已分配块。容量不足会明确失败，不依赖稀疏文件放大可用容量。格式化禁用 discard，避免回收刚预分配的空间。配置容量包含 ext4 元数据与日志开销，用户可用空间略小；界面应同时显示总容量和实际可用值。

总大小受镜像长度及 loop `sizelimit` 限制。挂载核对文件系统类型、UUID、镜像设备号与 inode、内核 loop 关联、挂载设备号和实际文件系统大小。任务不能访问底层文件或设备。真实写满行为仍须通过内核验收证明。

业务卷保持 `rw,nosuid,nodev`，允许运行共享安装工具和编译产物；对账明确拒绝 `noexec` 或只读漂移，不自动重新挂载或格式化来掩盖异常。`/tmp`、`/run` 的不可执行限制由容器运行配置单独实施。

## 状态与恢复

控制状态为 `reserved → allocating → formatting → formatted → ready`，清理为 `removing → removed`。外部变更之前先刷盘记录意图，复用节点的受保护文件、独占锁、原子替换和目录同步。

每用户只保留一份最高代次磁盘记录。下一代只能接续已 `removed` 且资源目录确实不存在的上一代，逻辑用户、电脑、节点及操作归属不变，代次严格加一；旧代、跳代、同代容量变更均拒绝。未建立物理磁盘的代次也由 `Remove` 持久记录 `removed`，不能以“没有目录”跳过关闭，否则连续验收会丢失代次边界。记录损坏或旧目录重新出现时停止，不自动覆盖或删除。

- `allocating` 可以恢复未完成的预分配，必须保持同一镜像 inode 与容量。
- 写入 `formatting` 意图后，恢复只核验 UUID 并执行只读完整性检查，不再次格式化镜像。无法证明初始化完整时，由开户补偿清理该代次后显式重试。
- 持久镜像丢失挂载时，`Inspect` 返回存在但未就绪，`Ensure` 核验原镜像并重新挂载，不重建文件系统。
- `formatted` 挂载后还必须完成子目录授权、复验及刷盘，才能保存 `ready`。挂载回包丢失时复用已核验挂载，只允许恢复初始权限的空目录，禁止修复非空异常目录。
- `Workspace.Exists` 表示持久资源存在，`Workspace.Ready` 表示挂载与布局均正确。已就绪磁盘的目录缺失、链接、身份或权限漂移均拒绝，不补建空 profile 掩盖数据丢失。节点在存储就绪前不启动容器；运行实例对应的挂载丢失时报告异常。
- 外来目录、错误 UUID、inode 被替换、符号链接、嵌套或叠加挂载、同一镜像的多个设备关联均拒绝自动修改。

loop 分配使用节点独占锁和 `--nooverlap`，因为查找空闲设备与关联并非跨进程原子动作。挂载或解除关联前，打开设备并核验内核关联，保持引用直到动作结束，防止设备编号被复用。[util-linux losetup 文档](https://man7.org/linux/man-pages/man8/losetup.8.html)

挂载身份来自 `/proc/self/mountinfo`，解析根、目标、设备号、类型和选项。[Linux 挂载记录说明](https://man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html) UUID 与魔数按内核公开结构检查。[ext4 超级块说明](https://www.kernel.org/doc/html/latest/filesystems/ext4/super.html)

## 清理与部署

本接口供首次开户补偿及节点专用验收清理使用。节点先确认容器已停止并删除、Docker 卷已删除，然后才调用磁盘清理。`Remove` 保存 `removing` 后正常卸载；忙挂载或未知结果会保留镜像。解除设备关联后继续有限等待并确认不再引用镜像，不能把 detach 命令返回成功当作已释放占用。

最后删除本代次镜像及空目录，刷盘父目录并保留 `removed` 记录；后续代次在同一记录中前向更新，不累计每代次的记录和锁。不使用强制或延迟卸载、全局解除关联及递归删除。已激活用户的删除、扩容、备份恢复和重建属于后续独立运维协议。

正式后端要求 Linux root 节点服务及受信发行版的 `fallocate`、`mkfs.ext4`、`e2fsck`、`losetup`、`mount`、`umount`。真实可执行路径必须由 root 所有且不可被普通用户改写。命令使用固定程序和参数数组、最小环境、输出上限、超时及进程组终止，不经过 Shell。

节点挂载必须对 Docker 守护进程可见，部署不能随意启用隔离挂载命名空间。必须检查挂载传播，并在用户容器内验证同一 UUID 和容量，避免绑定到空目录。节点 systemd 启动链及固定版本依赖引导已接通；真实首次部署与跨进程挂载验收仍未完成。

新布局与存储记录版本 1、2 均不兼容，旧版本记录在加载时拒绝且原样保留。启动逐批检查记录目录，旧名称、旧锁或未知条目会阻止启动并原样保留，不通过忽略旧记录、改名或删除屏障完成升级。正式部署使用全新状态；中间开发环境须先由原版本停单、排空并确认资源关闭，保存备份后另建空环境。回滚必须使用理解版本 3 存储记录、版本 3 节点生命周期及镜像布局 2 的配套程序和状态；旧版本只能恢复原有环境快照，不能访问或转换新布局。本项不涉及数据库迁移。

备份应在排空任务后同步镜像、控制记录和业务数据库。恢复时先停止旧容器并核对身份。应用回滚不重新格式化镜像、不删除控制记录，也不自动降级文件系统格式。

## 验证方式与当前证据

常规 `make lint check test` 覆盖状态机、结果未知恢复、容量不足、忙挂载与延迟解除关联、错误路径和 inode、挂载记录解析，以及脚本不能自动提升权限和内核失败时保留资源。增加连续 12 代模拟物理磁盘、24 代空资源关闭、跨代次稳定锁、重启、旧代/跳代/身份漂移、关闭目录重现及旧布局拒绝回归。成功的 loop 与挂载路径仍使用明确替身，不能替代内核验收。

[verify_storage.py](../../scripts/verify_storage.py) 使用本地已有的固定摘要 Linux 镜像，只创建专属容器及空白卷，不挂载开发者已有目录、数据库或 Docker socket：

```sh
python3 scripts/verify_storage.py \
  --docker "$TOM_TEST_DOCKER_BIN" \
  --socket "$TOM_TEST_DOCKER_SOCKET" \
  --image "$TOM_TEST_STORAGE_IMAGE" \
  --mode image
```

`image` 模式无网络、系统层只读、移除全部 Linux capabilities。已实际验证 512 MiB 预分配、固定 UUID、ext4 格式和只读完整性检查，容器和卷均已回收。这不代替挂载后的容量约束验证。

`kernel` 模式在明确授权的专属测试环境中使用 `--mode kernel --allow-kernel`，需要临时 `--privileged` 容器，验证真实挂载、写满拒绝、持久化、重新挂载、占用拒删及设备回收。失败时停止容器并保留卷和控制记录，避免删除仍被内核引用的镜像。自动审批已拒绝此前高权限探针，该模式等待明确授权，尚无通过证据。
